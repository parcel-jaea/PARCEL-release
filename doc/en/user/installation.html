4 Installation

This chapter describes how to install SYCL PARCEL.
PARCEL consists of header files only. It can be used simply by including ./Include/parcel_sycl.hpp and compiling with a SYCL-capable compiler. No prebuilding or installation as a library is required.

Note, however, the following three points.

  • In C++, C and Fortran, MPI is used by default (PARCEL_MPI defaults to 1). The SYCL compiler (acpp) is invoked through an MPI wrapper (mpicxx, etc.). A single-process version without MPI can be built with -DPARCEL_MPI=0. Python and spack default to no MPI (“Default of MPI”, “Build without MPI”).
  • The eigenvalue solver ks_arnoldi (Include/parcel_krylov_ks.hpp) includes lapacke.h and calls LAPACKE. Since all solvers are enabled by default, the LAPACKE header and library must be specified even when only linear systems are solved. Excluding ks_arnoldi with -DPARCEL_ENABLE_KS_ARNOLDI=0 removes this requirement (“Selecting the Solvers to Build”).
  • The #include directives in the source use relative paths. Compile the sample programs in the PARCEL top-level directory.

For installing a SYCL-capable compiler, see the previous chapter. Installing PARCEL together with its prerequisites with spack is described in “Installing with spack”, and the Python package in “Python Package”.

4.2 Checking After the Build

To check a build, use bash examples/run_quick_checks.sh. It builds the four Quick Start examples (C++, C, Fortran and Python) with examples/build_examples.sh, runs them as one process, and with an MPI build also runs the C++ example with two processes. Each example prints check: ... PASS if the maximum relative error against the exact solution is at most 1e-6 (“Program Overview”). At the end, the script prints PASS n / FAIL m (SKIP k) and the elapsed time on one line, and exits with status 0 if nothing failed. The Python example is SKIPPED (not failed) if parcel (with NumPy and SciPy) cannot be imported.

The build (build_examples.sh quick) runs the SYCL compilations (the C++ example and the wrapper of the C / Fortran API) at the same time (the number of concurrent compilations is BUILD_JOBS; the default is the smaller of the number of targets and the number of cores). After a successful build, the build settings (SYCL_TARGET, CXXFLAGS, PARCEL_MPI, the compilers and their locations, etc.) and the cksum of the sources (headers, API, examples) are recorded in examples/build/build_stamp.txt. From the second run on, if the executables exist and the record matches the current state, the build is skipped and only the runs are performed (less than a minute). If a setting or a source has changed, the differing items are shown and the examples are rebuilt. --rebuild always rebuilds.

export OMPI_CXX=acpp
bash examples/run_quick_checks.sh                 # with MPI. last line: === PASS 6 / FAIL 0 (SKIP 0)  所要 <sec> s
PARCEL_MPI=0 bash examples/run_quick_checks.sh    # without MPI
bash examples/run_quick_checks.sh --rebuild       # rebuild
NO_BUILD=1 bash examples/run_quick_checks.sh      # run examples/build/ as is, without checking the record

The environment variables for the compilers, target and LAPACK are the same as for build_examples.sh (for a GPU, e.g. SYCL_TARGET=--acpp-targets=cuda:sm_70). The MPI launcher is set with MPIEXEC (default mpirun), MPIEXEC_NP_FLAG (default -n), MPI_NP (default 2) and MPIEXEC_ARGS. For MPI libraries that cannot run MPI_Init without the launcher (e.g. Fujitsu MPI), MPIEXEC_ALL=1 starts the single-process runs through the launcher as well. Fujitsu mpiexec writes the standard output of the ranks to the job log, where the check lines cannot be read, so with Fujitsu mpiexec (MPIEXEC=mpiexec whose real file is under /opt/FJSV…) RC_ONLY=1 (pass if the exit status is 0) is the default (use RC_ONLY=0 to turn it off). When installed with spack, spack test run parcel-sycl py-parcel-sycl performs the same check (“Installing with spack”).

Number of threads and where it runs. If OMP_NUM_THREADS is not set, all available logical CPUs are used on a compute node (inside a job), and 4 on a login node (or the number available, if fewer than 4). For the MPI run this is divided by the number of processes so that the total stays the same (at least 1; 2 processes on a login node get 2 threads each). The number of available logical CPUs is the smallest of the CPU affinity (nproc), the CPU limit of the cgroup, and the job’s allocation on this node (PBS NCPUS, Slurm SLURM_CPUS_ON_NODE). Whether it is a compute node is decided by the presence of a job environment variable (PBS PBS_JOBID, Fujitsu PJM PJM_JOBID, Slurm SLURM_JOB_ID), and can be forced with QUICK_NODE=compute / QUICK_NODE=login. The decision and the values used are printed first. If OMP_NUM_THREADS is set, its value is used (in a job the scheduler may set it: PBS ompthreads (a queue default of 1 is possible), Fujitsu PJM --omp thread=). With Open MPI, --bind-to none is added unless MPIEXEC_ARGS specifies a placement (--bind-to, --map-by) (with 2 or fewer processes Open MPI binds each process to one core, which would pack several threads onto one core).

Where to run it. In CPU environments, a login node is fine (follow the rules of the site). In GPU environments and on A64FX (Odyssey), run it on a compute node (a short batch job or an interactive job): login nodes have no GPU, and A64FX executables do not run on the x86 login nodes. When the MPI run (2 processes) is done in a GPU environment, the script does not assign one GPU per process (as gpu_bind.sh in “Mapping One Rank to One Device” does), so both processes may use the same GPU.

4.4 Macros

Since PARCEL is a header-only library, the configuration and behavior of the library (Include/) can be selected by adding -D<macro> or -D<macro>=<value> when compiling the user program. Every macro works with its default value, and normally nothing needs to be specified. There are the following four kinds by purpose.

  • Selecting the solvers to build: exclude unused solvers to shorten compilation
  • Integer type: select the widths of the global indices (64-bit by default) and the rank-local indices (32-bit by default)
  • Optimization: select the loop structure of the kernels for each environment, and, since the defaults reduce memory, optimization options that use more memory for speed (Optimization)
  • Checks and numerical operations: checks that prevent wrong results and the method of double-double operations (keep the defaults; Checks and Numerical Operations)

In addition, there are macros for diagnosis and isolation, which are not specified in normal builds.

4.4.1 Selecting the Solvers to Build (Include/parcel_solver_select.hpp)

All solvers are enabled by default, and normally nothing needs to be specified. Because all solvers go into a single translation unit, compilation takes a long time (6–14 minutes per configuration on A64FX); when the solvers to be used are known, for example during troubleshooting, disabling the others shortens the compilation.

Each macro builds the solver when set to 1 and excludes it when set to 0. A solver macro that is not specified takes the value of PARCEL_ENABLE_ALL_SOLVERS (default 1), so all solvers are built when nothing is specified. To build only some solvers, set PARCEL_ENABLE_ALL_SOLVERS=0 and set the solvers to be built to 1.

Macro Default Description
PARCEL_ENABLE_ALL_SOLVERS 1 Value used for each solver macro below when it is not specified. If set to 0, only the solvers set to 1 are built
PARCEL_ENABLE_PCG 1 (the value of PARCEL_ENABLE_ALL_SOLVERS) parcel::krylov::pcg
PARCEL_ENABLE_PBICGSTAB 1 (the value of PARCEL_ENABLE_ALL_SOLVERS) parcel::krylov::pbicgstab
PARCEL_ENABLE_PGMRES 1 (the value of PARCEL_ENABLE_ALL_SOLVERS) parcel::krylov::pgmres
PARCEL_ENABLE_PCAGMRES 1 (the value of PARCEL_ENABLE_ALL_SOLVERS) parcel::krylov::pcagmres (including the variant that does not form QQ, CAGMRES_Q_IMPLICIT)
PARCEL_ENABLE_POWER 1 (the value of PARCEL_ENABLE_ALL_SOLVERS) parcel::krylov::power
PARCEL_ENABLE_INVERSE_POWER 1 (the value of PARCEL_ENABLE_ALL_SOLVERS) parcel::krylov::inverse_power
PARCEL_ENABLE_KS_ARNOLDI 1 (the value of PARCEL_ENABLE_ALL_SOLVERS) parcel::krylov::ks_arnoldi. If set to 0, LAPACKE is no longer required (except for the verification sample)

Dependencies are resolved automatically: enabling inverse_power enables pcg and pgmres, and enabling ks_arnoldi enables pgmres. If no solver is enabled, a compile error occurs. There is no macro named PARCEL_ENABLE_CHOLQR_PCAGMRES; specifying it causes a compile error (#error).

# build only pgmres (exclude all others)
-DPARCEL_ENABLE_ALL_SOLVERS=0 -DPARCEL_ENABLE_PGMRES=1
# exclude only ks_arnoldi (build all others)
-DPARCEL_ENABLE_KS_ARNOLDI=0

4.4.2 Integer Type

Integers such as row indices, column indices and numbers of nonzeros are held in the type of the macro PARCEL_INT for global indices, and in the type of the macro PARCEL_LINT for indices within one rank (such as the CRS on the device). By default, PARCEL_INT is 64 bits (int64_t; MPI_INT64_T in MPI communication) and PARCEL_LINT is 32 bits (int32_t, MPI_INT32_T). The reasons for these defaults (integer overflow in large problems and the speed of the local kernels) are given in “Integer Type” in the Basic Structure chapter.

Specification PARCEL_INT PARCEL_LINT Notes
None (default) int64_t int32_t
-DPARCEL_LOCAL_INT64 int64_t int64_t -DPARCEL_LOCAL_INT64=0 is the same as the default
-DPARCEL_INT32 int32_t int32_t -DPARCEL_INT32=0 is the same as the default
-DPARCEL_INT int64_t int32_t Former way to make PARCEL_INT 64-bit. Accepted for compatibility (its value is not used)
Both -DPARCEL_INT and -DPARCEL_INT32 — — Contradictory; stopped with #error
Both -DPARCEL_INT32 and -DPARCEL_LOCAL_INT64 — — The rank-local type would be wider than the global type; stopped with #error

The selected widths are available as the macros PARCEL_INT_BITS and PARCEL_LINT_BITS (64 or 32 each).

How to choose the type (the range of matrices, integer overflow in large problems, the effect on memory and on the speed of the local kernels, and the relation to the C and Fortran APIs) is described in “Integer Type” in the Basic Structure chapter.

4.4.3 Optimization

The macros of optimizations that increase speed without changing the computation (the algorithm and the number of iterations) are listed below: those that select the loop form of the kernels (the first eight) and those that make the solvers faster by using more memory (the last two; optimization options). How each optimization works, its effects and the defaults per environment are described in the “Optimization” chapter, and the compile commands per environment in Recommended Options. The defaults reduce memory.

Macro Default Description

_BLOCKING_LOOP_DOT_ 0 If 1, replaces only the reductions (dot, dddot, max) with blocked versions. For CPUs other than A64FX. Do not specify on GPUs

PARCEL_PRECON_LADDER 0 (the value of PARCEL_SPMV_LADDER) Ladder splitting of the iteration loops of the Jacobi preconditioner. Set explicitly to 0 on A64FX
PARCEL_GEMV_AS_AXPY 0 (the value of _BLOCKING_LOOP_) If 1, decomposes gemv into M axpy operations (Decomposing gemv). Changes the rounding order
PARCEL_A64FX_AXPY_C 1 If 1, uses the versions of the axpy that takes coefficients by value and of the axpy decomposition of gemv rewritten for A64FX (C in Optimizations for A64FX). 0 gives the form before the rewrite. The results do not change. Effective only in _BLOCKING_LOOP_ builds
PARCEL_CG_FUSED 0 (the value of _BLOCKING_LOOP_) If 1, fuses the kernels of one iteration of pcg (the updates of xx and pp, the update of rr and ⟨r,r⟩\langle r, r \rangle; D in Optimizations for A64FX). The results do not change. Can be 1 only in _BLOCKING_LOOP_ builds

The results do not change. Not used for a double-precision preconditioner matrix or with on-the-fly computation
PARCEL_JACOBI_ONTHEFLY 1 (0 for A64FX) The Jacobi preconditioner (PRECON_JACOBI) does not keep the values of B=DA−1RB = D_A^{-1}R and computes them from the values of AA and DA−1D_A^{-1} at every application. The run-time environment variable PARCEL_PSTEP takes precedence

4.4.4 Default Orthogonalization of ks_arnoldi

The orthogonalization of the Arnoldi process of ks_arnoldi (Krylov-Schur method in the eigenvalue solver chapter) is selected in the program with set_qr_algo() (set_qr_algo() of ks_arnoldi in the API Reference). The following macro selects at build time the default used when it is not called. The environment variable PARCEL_KS_ORTHO is not read (if it is set, rank 0 prints a one-line warning to standard error at the first solver(); the behavior does not change).

Macro Default Description
PARCEL_KS_ORTHO_DEFAULT undefined (cgs2) cgs2 (classical Gram-Schmidt twice) or mgs (modified Gram-Schmidt twice). The build for PS-A (the spack environment psa, variant ks_ortho=mgs) uses mgs. When undefined, CGS2 (QR_CGS). A value given with set_qr_algo() takes precedence

4.4.5 Checks and Numerical Operations

These macros select checks that prevent wrong results and the method of double-double operations. Keep the defaults; removing the checks can silently return wrong results, so specify them only when you understand the reasons.

Macro Default Description
PARCEL_REQUIRE_IN_ORDER 1 At the entry of set_crsMat() and of solver() of each solver, checks that the SYCL queue is in-order, and throws std::invalid_argument on violation (including when there is no queue). PARCEL submits kernels to one queue in order without sycl::event or depends_on, and each kernel reads the results of the previous one, so in-order execution is assumed. With the SYCL 2020 default (out-of-order) queue, the execution order of USM kernels that use no accessors is not guaranteed. 0 disables the check
PARCEL_NO_CRS_CHECK 0 1 disables the input checks of set_crsMat() (the normal version and the hi/lo version for double-double). The checks are: the local number of rows n equals nend-nstart+1 and is at least one (a rank with zero rows is not supported); rowptr[0] == 0, it is non-decreasing, and rowptr[n] == nnz; the row blocks of all ranks cover all rows without gaps or overlaps (in any rank order); and the column indices are within the global number of rows. The non-MPI version checks only rowptr and the column indices. On violation all ranks throw the same std::invalid_argument (the message names the offending rank and what is wrong). The cost is one pass over the nonzeros and two collective communications. If the checks are disabled and a broken input is given, the result is silently wrong because uninitialized receive buffers of the halo exchange are used, or memory outside the arrays is read
PARCEL_ALLOW_FAST_MATH Undefined If defined, allows builds with -ffast-math / -ffinite-math-only (__FAST_MATH__ / __FINITE_MATH_ONLY__). By default parcel_sycl.hpp stops with #error. Rewriting expressions by associativity eliminates the error terms of double-double, and dd silently falls to double precision. In addition, the NaN / Inf checks (std::isfinite) are removed and DIVERGED_NANORINF no longer works. If defined, the precision of dd and the detection of NaN are not guaranteed
PARCEL_DD_NO_FMA Undefined If defined, replaces the error-free transformation of double-double products (TwoProd) by fma (p=fma(a,b,0)p = \mathrm{fma}(a,b,0), e=fma(a,b,−p)e = \mathrm{fma}(a,b,-p), the default) with Dekker splitting. For CPUs without FMA instructions. Do not use it on GPUs (CUDA), where Dekker splitting breaks

Do not use -fno-exceptions either. It is incompatible with the argument checks (std::invalid_argument, etc.).

4.5.3 Odyssey

On A64FX, the login nodes and compute nodes have different architectures, so the build is done on a compute node. An example build job script is shown below. The MPI wrapper mpiFCC is used, and OMPI_CXX=acpp makes it invoke acpp. With the omp.library-only target, acpp uses the Fujitsu compiler given in ACPP_CPU_CXX as the host compiler. As in the other environments, the location of the LAPACKE header is specified with -I/usr/include/openblas (with this, the build works on the compute node), and Fujitsu’s libfjlapack is used as the implementation.

#!/bin/bash
#PJM -L "rscgrp=short-o"
#PJM -L "node=1"
#PJM -L "elapse=2:00:00"
#PJM -g <group>
#PJM --omp thread=48
#PJM -j

# Environment: apply "Settings for use" of "Odyssey" in the chapter "Installing a SYCL Compiler"

cd ${PJM_O_WORKDIR}
LINKOPT="-L$fj_root/lib64 -Wl,-rpath,$fj_root/lib64 \
  -L$sycl_root/lib -Wl,-rpath,$sycl_root/lib \
  -L$llvm_root/lib -Wl,-rpath,$llvm_root/lib -lfjlapack"

mpiFCC -O3 -std=c++17 --acpp-targets=omp.library-only \
  -D_BLOCKING_LOOP_=1 -DPARCEL_SPMV_LADDER=1 -DPARCEL_PRECON_LADDER=0 \
  -ffp-contract=fast \
  -I/usr/include/openblas \
  -o verify_double tests/verify/parcel_krylov_sample_verify.cpp ${LINKOPT}

A single build takes longer than on Xeon and needs several GiB of memory. The memory available to a single-node job is 28 GiB, so limit the number of concurrent builds when building several precision configurations at the same time.

-ffp-contract=fast makes the compiler fuse multiply-adds (a×b+ca \times b + c) into FMA instructions. The clang mode of the Fujitsu compiler does not fuse them by default. AdaptiveCpp passes the command-line -O3 to the Fujitsu compiler after ACPP_OMP_CXX_FLAGS, so the -Kfast in ACPP_OMP_CXX_FLAGS is canceled by the later -O3 and does not take effect. If fast-math is enabled, for example by passing -Kfast without a later -O3, double-double and the NaN detection break, so PARCEL stops the build with #error (“Do Not Use -ffast-math”). -ffp-contract=fast on the command line reaches the Fujitsu compiler. On one node of Odyssey (4 ranks × 12 threads, NX=256, pcg + Jacobi preconditioner), one iteration became 3 % faster (SpMV 10 %, the body of axpy 25 %). The number of iterations does not change, and the results change in the last digits (about 1e-11 relative in the residual). FMA adds without rounding the product, so the results are not bit-identical to a build without the flag. Use -ffp-contract=off if the results must agree. Inside the double-double functions, Include/ddlib.hpp still prohibits FMA (last paragraph of this section).

In builds for A64FX (-D_BLOCKING_LOOP_=1), the Jacobi preconditioner stores the values of BB by default (“Without H” in Choosing Between Memory and Speed; the default of PARCEL_JACOBI_ONTHEFLY is 0, so nothing needs to be specified). On A64FX the on-the-fly computation (a multiplication and a diagonal check per nonzero) shows up in the preconditioner time: on one node of Odyssey (NX=256, pcg + Jacobi preconditioner), storing the values makes the preconditioner section 0.77 times and the total time to convergence 0.81 times. In exchange, the memory grows by the size of the preconditioner matrix precision per nonzero of AA (8 bytes in double precision). To reduce memory, specify -DPARCEL_JACOBI_ONTHEFLY=1 explicitly.

At run time, set OMP_WAIT_POLICY=ACTIVE and KMP_BLOCKTIME=infinite, which keep the OpenMP threads spinning while they wait (recommended; this is not a library default, so set it in the job environment). On one node of Odyssey (4 ranks × 12 threads, one rank per CMG), the fixed cost per iteration that does not depend on the problem size drops from 5.2 ms to 3.0 ms. It helps when the number of rows per device is small. Waiting threads keep using their cores, so it is counterproductive when processes compete for cores (for example, other processes sharing the node). Together with the rewritten axpy and the fused pcg kernels that are enabled in this build, the effects and caveats are described in Optimizations for A64FX.

In code before 2026-10-10, the prohibition of FMA for the double-double arithmetic (#pragma clang fp contract(off)) did not end at the end of ddlib.hpp with the Fujitsu compiler, so no FMA instructions were used in any of the following kernels (the clang mode of the Fujitsu compiler does not know the push / pop of float_control). The current code limits the prohibition to the double-double functions, and the other kernels use FMA as the compiler options say (-ffp-contract=fast above). Results in double precision and other precisions differ from earlier builds in the last digits.

4.5.9 C and Fortran Programs

Programs that use the C or Fortran API compile the wrapper capi/wrapper_parcel_sycl.cpp with the same flags as the mpicxx command of each environment above (--acpp-targets, kernel optimization, LAPACKE), and link it with the C or Fortran main program using the SYCL compiler. Use the same --acpp-targets for compiling and linking the wrapper. acpp (clang) links as PIE, so add -fPIE to objects built with gcc or gfortran. An example for s86 CPU (Open MPI) follows; in other environments, replace the flags on the first line by those of the environment.

# Environment: apply "Settings for use" of "s86" in the chapter "Installing a SYCL Compiler"
FLAGS="-O3 --acpp-targets=omp -march=native -mtune=native -D_BLOCKING_LOOP_DOT_=1"
mpicxx ${FLAGS} -I/usr/include/openblas -c capi/wrapper_parcel_sycl.cpp -o wrapper_parcel_sycl.o

# C
mpicc  -O2 -fPIE -Icapi -c prog.c -o prog.o
mpicxx --acpp-targets=omp -o prog prog.o wrapper_parcel_sycl.o -lopenblas -lm

# Fortran (compile the PARCEL module first)
mpif90 -O2 -fPIE -c capi/parcel_sycl_mod.f90 -o parcel_sycl_mod.o
mpif90 -O2 -fPIE -c prog.f90 -o prog.o
mpicxx --acpp-targets=omp -o prog prog.o parcel_sycl_mod.o wrapper_parcel_sycl.o \
       $(mpif90 --showme:link) -L$(dirname $(mpif90 -print-file-name=libgfortran.so)) -lgfortran -lopenblas
  • The MPI Fortran libraries to add at link time are obtained from the MPI wrapper (mpif90 --showme:link for Open MPI, mpif90 -show for Intel MPI).
  • On PS-A and PS-B, specify LAPACKE (-I and -l:libopenblaso.so.0) as in the sections above. With Intel MPI on PS-A, use mpif90 (gfortran inside) as the Fortran wrapper.
  • With Fujitsu Fortran (frt, mpifrt) and Fujitsu C (fcc, mpifcc), add -Kopenmp (Fortran in “Usage”).
  • examples/build_examples.sh builds the samples in examples/ with the same steps. The compilers, target and LAPACK are changed with environment variables (SYCL_TARGET, CXXFLAGS, LAPACK_INC, LAPACK_LIB, MPICXX / MPICC / MPIFC, FC_LINK).

4.6 Default of MPI

Whether PARCEL is built with MPI or as the single-process version without MPI is decided by the macro PARCEL_MPI (1: with, 0: without). The default differs by usage as follows.

Usage Default of PARCEL_MPI Where it is decided How to build without / with MPI
C++ (including Include/parcel_sycl.hpp) 1 (with MPI) Headers in Include/ Add -DPARCEL_MPI=0
C (capi/parcel_sycl_c.h) 1 (with MPI) parcel_sycl_c.h and the wrapper Add -DPARCEL_MPI=0 to both the wrapper and the main program
Fortran (capi/parcel_sycl_mod.f90) 1 (with MPI) The wrapper (the module does not depend on MPI) Add -DPARCEL_MPI=0 to the wrapper and satisfy use mpi with the substitute module
examples/build_examples.sh 1 (with MPI) Environment variable PARCEL_MPI PARCEL_MPI=0 bash examples/build_examples.sh
Python (python/, pip) 0 (without MPI) python/CMakeLists.txt -C cmake.define.PARCEL_MPI=1 for MPI
spack (parcel-sycl, py-parcel-sycl) 0 (without MPI; variant ~mpi) The recipe variant mpi +mpi for MPI

C++, C and Fortran default to MPI so that programs written as for v1.0 (compiled with the MPI wrappers and started with mpirun) run as they are. Python and spack default to no MPI so that the package can be installed and tried immediately on machines without MPI (local computers, macOS, etc.). To use the version with MPI, specify it as above. In C and Fortran, if the wrapper and the main program are built with different settings, the types of the communicator argument do not match and the program does not work correctly (this is not detected at link time), so build both with the same setting. C++ is a header-only library, so the setting of the user program is used as it is. The computation is the same in both versions, and the results of the MPI version run with one process and of the version without MPI agree bit for bit.

4.7 Build without MPI

With -DPARCEL_MPI=0, a single-process version that does not use MPI can be built. It does not include mpi.h or link the MPI library, so compile it directly with the SYCL compiler (acpp, etc.) instead of the MPI compiler wrapper (mpicxx), and run it without mpirun. Without the option (the default), MPI is used. The computation is the same as running the MPI build with one process, and the results agree bit for bit.

acpp -O3 --acpp-targets=omp -march=native -DPARCEL_MPI=0 \
  -I/usr/include/openblas -o quick_start examples/quick_start.cpp -lopenblas
./quick_start

# the four programs in examples/ (C / Fortran are compiled with gcc / gfortran)
PARCEL_MPI=0 bash examples/build_examples.sh

To build C and Fortran programs by hand, add -DPARCEL_MPI=0 to both the wrapper and the C main program, and use acpp, gcc and gfortran instead of the MPI wrappers (mpicxx, mpicc, mpif90). use mpi in Fortran is satisfied by the single-process substitute module examples/sample_f_mpi_stub.f90 (which implements MPI_Init, MPI_Comm_rank, MPI_Comm_size, MPI_Finalize and others for one process). Example commands are in the “without MPI” parts of “C” and “Fortran” of the Quick Start.

User programs are written in the same way as with MPI. The differences are:

  • C++: create the communicator with parcel::comm comm(&q); (corresponding to parcel::comm comm(MPI_COMM_WORLD, &q); with MPI). mpi_rank() returns 0 and mpi_size() returns 1. set_crsMat(&comm, nstart, nend, n, nnz, ...) can be used as is, but since one process owns everything, use nstart = 0 and nend = n - 1 (otherwise std::invalid_argument). Functions that use MPI types (comm::mpi_comm(), etc.) do not exist. Guard the MPI calls in the user program (MPI_Init, etc.) with #if PARCEL_MPI (see examples/quick_start.cpp).
  • C: compile both the wrapper (capi/wrapper_parcel_sycl.cpp) and the program that includes parcel_sycl_c.h with -DPARCEL_MPI=0 (otherwise the type of the communicator argument does not match). The function names and argument order are unchanged; the communicator argument (PARCEL_C_COMM) becomes int and its value is ignored (pass 0). Use nstart = index_base and n_local = n_global (otherwise PARCEL_ERR_DISTRIBUTION). Exceptions inside the library do not call MPI_Abort; a message is printed and PARCEL_ERR_RUNTIME is returned. MPI_Init is not needed.
  • Python: the version without MPI is the default (Python Package in “Installation”). Run with python script.py without mpirun.
  • Fortran: use capi/parcel_sycl_mod.f90 as is (the communicator integer is ignored). Compile examples/sample_f.f90 unchanged together with examples/sample_f_mpi_stub.f90, a single-process substitute for the mpi module, using gfortran.

4.9 Installing with spack

spack/ in the distribution package contains recipes for installing PARCEL with spack, and a script that installs everything from scratch, from fetching spack through LLVM, AdaptiveCpp, OpenBLAS and Python to PARCEL. The original description is spack/README.md. The target is spack 1.x (package repository API v2.2).

4.9.1 Recipes

Package Contents
parcel-sycl Headers (include/), C API (lib/libparcel_sycl_c.so and include/parcel_sycl_c.h), Fortran module (include/parcel_sycl_mod.mod and lib/libparcel_sycl_f.a)
py-parcel-sycl The Python package parcel (builds python/ with scikit-build-core; “Python Package”)

The variants are common to both.

Variant Default Meaning
mpi off With MPI (the default is the single-process version without MPI)
cuda + cuda_arch=<n> off --acpp-targets=cuda:sm_<n>. With cuda_arch=70 (V100), -Xcuda-ptxas -maxrregcount=255 is added automatically
rocm + amdgpu_target=<gfx> off --acpp-targets=hip:<gfx>
(neither cuda nor rocm) --acpp-targets=omp (CPU)
native on -march=native -mtune=native
kernel auto Kernel optimization (“Optimization”): auto (blocking_dot on CPUs, ladder on AMD GPUs (+rocm), none on NVIDIA GPUs (+cuda), a64fx for +fj), blocking_dot, a64fx, ladder, none
fj off For A64FX: compiles the host side with the Fujitsu compiler (FCC) and builds the Fortran module with frt (confirmed with the Odyssey definition wis_ody). Adds -std=c++17 -ffp-contract=fast (Recommended Options)
capi (parcel-sycl only) on Builds the C / Fortran API
scipy (py-parcel-sycl only) on Also installs SciPy (used by DistributedCSR.from_scipy() / from_global() and examples/quick_start.py; corresponds to parcel[scipy] with pip)
ks_ortho cgs2 Default orthogonalization of ks_arnoldi (“Default Orthogonalization of ks_arnoldi”). mgs adds -DPARCEL_KS_ORTHO_DEFAULT=mgs (also in PARCEL_CXXFLAGS). A value given by the program with set_qr_algo() takes precedence. py-parcel-sycl is built with parcel-sycl of the same value

To add them to an existing spack environment, use the local distribution package with spack develop.

spack -e <env> repo add <package>/spack/spack_repo/parcel
spack -e <env> config add "concretizer:unify:when_possible"          # when installing CPU and GPU versions side by side
spack -e <env> develop --no-clone --path <package> parcel-sycl@1.2.0
spack -e <env> develop --no-clone --path <package> py-parcel-sycl@1.2.0
spack -e <env> add "parcel-sycl@1.2.0 ~mpi ~cuda ~rocm" "py-parcel-sycl@1.2.0 ~mpi ~cuda ~rocm"                    # CPU
spack -e <env> add "parcel-sycl@1.2.0 ~mpi +cuda cuda_arch=70" "py-parcel-sycl@1.2.0 ~mpi +cuda cuda_arch=70"     # GPU
spack -e <env> concretize -f && spack -e <env> install

To use them, spack load with the configuration specified. spack load parcel-sycl sets PARCEL_CXXFLAGS (target, optimization, with or without MPI, header location) and PARCEL_LDFLAGS (RPATHs of the libraries needed at run time (LLVM libomp, AdaptiveCpp, LAPACK, MPI) and LAPACK) so that user programs are compiled with the same settings as PARCEL. The version with MPI also sets OMPI_CXX=acpp etc., so compile with mpicxx in the same way. The RPATH of libomp is not added through the MPI wrapper, so always add PARCEL_LDFLAGS. spack load does not set the locations of the headers (parcel_sycl_c.h, parcel_sycl_mod.mod) and libraries of the C and Fortran APIs; find them with spack location -i and give them with -I, -L and -Wl,-rpath.

spack env activate <env>
spack load parcel-sycl+cuda py-parcel-sycl+cuda                   # load with the configuration specified
acpp $PARCEL_CXXFLAGS -O3 -o prog prog.cpp $PARCEL_LDFLAGS        # C++
P=$(spack location -i parcel-sycl+cuda)                           # C (version without MPI): give the location yourself
gcc -I$P/include -o prog prog.c -L$P/lib -lparcel_sycl_c -Wl,-rpath,$P/lib
python script.py                                                  # Python

Notes:

  • Specify the root specs down to ~cuda ~rocm. With only parcel-sycl ~mpi, unification may merge it with the GPU version.
  • CPU and GPU versions in the same environment collide in the view, so exclude parcel-sycl and py-parcel-sycl from the view of the environment (view: default: {root: .spack-env/view, exclude: [parcel-sycl, py-parcel-sycl]}).
  • Adding specs to an already concretized environment may cause an internal error (unsatisfiable) in concretize. Re-concretize with concretize -f.
  • Use a single MPI and a single hipsycl (AdaptiveCpp) in an environment (packages:mpi:require: including the version and configuration, packages:hipsycl:require:). With several external MPIs, another configuration (such as a CUDA build) may be selected.
  • The CUDA used by AdaptiveCpp is recorded from ACPP_CUDA_PATH (or the spack cuda) at build time, and spack load sets the same value. To avoid a CUDA newer than the driver, specify it as the external cuda package or with this variable.
  • The LAPACKE headers are copied to include/lapacke/ (for systems whose compute nodes lack lapacke.h).
  • Running tests inside the spack develop source (which creates bin/, __pycache__, etc.) makes spack consider it modified, and PARCEL is rebuilt at the next install. Run tests in a copy of the source.

4.9.2 Installing from the Distribution Tarball

The recipes hold the url and sha256 of the distribution tarball. The url points to the tarball on the GitHub Release (https://github.com/parcel-jaea/PARCEL-release/releases/download/v1.2.0/parcel_sycl-1.2.0.tar.gz), and tools/make_tarball.py --pin writes the sha256 into the recipes (“Verifying the Distribution”). Without spack develop, spack fetches the tarball from the url (parcel-sycl and py-parcel-sycl use the same tarball). When the computer cannot connect to the outside, place the tarball in the layout of a spack mirror (<mirror>/_source-cache/archive/<first two characters of the sha256>/<sha256>.tar.gz) and register it with spack mirror add. spack checks the fetched tarball against the sha256 in the recipe and stops if it differs. The sha256 is part of the spack hash, so rewriting it rebuilds PARCEL (also when it is used with spack develop). The procedure is given in the section “Installing from the Release Tarball” of spack/README.md.

4.9.3 Choosing the Configurations

The configurations to install are chosen by the combination of packages (parcel-sycl, py-parcel-sycl) and variants (the spec). Examples of specs by purpose are shown below (the version @1.2.0 is omitted).

Purpose Spec
CPU, without MPI (C++, C, Fortran) parcel-sycl ~mpi ~cuda ~rocm
CPU, with MPI parcel-sycl +mpi ~cuda ~rocm
NVIDIA GPU (example: A100) parcel-sycl ~mpi +cuda cuda_arch=80
NVIDIA GPU, with MPI parcel-sycl +mpi +cuda cuda_arch=80
AMD GPU (MI300A) parcel-sycl ~mpi +rocm amdgpu_target=gfx942
C++ (headers) only, without the C and Fortran APIs parcel-sycl ~capi ~mpi ~cuda ~rocm
Python as well Add py-parcel-sycl with the same configuration (e.g., py-parcel-sycl ~mpi ~cuda ~rocm)
  • Choosing languages: C++ (headers) is always installed with parcel-sycl. The C and Fortran APIs are installed or omitted together by the variant capi (on by default); one of them alone cannot be chosen. Python is chosen by whether the separate package py-parcel-sycl is added.
  • With +capi (the default), a Fortran compiler is required (to build the Fortran module). On systems without a Fortran compiler, use ~capi.
  • py-parcel-sycl uses parcel-sycl for its build, so parcel-sycl is installed even when only Python is wanted. In that case parcel-sycl has the default +capi. On systems without a Fortran compiler, add the variant of parcel-sycl, as in py-parcel-sycl ~mpi ~cuda ~rocm ^parcel-sycl ~capi (confirmed on s86 that it concretizes and that parcel-sycl then no longer uses a Fortran compiler). OpenBLAS, used for LAPACK, also uses a Fortran compiler by default, so on systems with no Fortran compiler at all also specify openblas ~fortran (as in the Odyssey definition wis_ody).
  • +cuda and +rocm cannot be specified together (the recipe raises an error). Without either, the CPU (OpenMP) version is built. For GPUs, specify one cuda_arch (CUDA compute capability: V100 70, A100 80, GH200 90) or amdgpu_target.
  • +mpi requires MPI. Register the system MPI as an external package in the environment definition (use a single MPI and a single hipsycl in an environment; notes above).
  • mpi, cuda, rocm, etc. of py-parcel-sycl must match those of the parcel-sycl it is combined with (the recipe requires parcel-sycl with the same configuration).

With installation from scratch, the configurations installed are those listed in specs: of spack/stack/envs/<env>/spack.yaml. The bundled definitions list all configurations available on each system (for example, 8 lines on s86: CPU / GPU × without / with MPI × parcel-sycl / py-parcel-sycl). To narrow or change the configurations, edit specs: before running install_stack.sh. For example, to install only C++, C, Fortran and Python for the CPU with MPI, write as follows. If the list is edited after installation, rerunning install_stack.sh with the same command re-concretizes and installs only what is missing.

spack:
  specs:
  - parcel-sycl@1.2.0 +mpi ~cuda ~rocm         # CPU with MPI (C++, C, Fortran)
  - py-parcel-sycl@1.2.0 +mpi ~cuda ~rocm      # Python with the same configuration

4.9.4 Installing from Scratch

Without an existing spack, spack/stack/install_stack.sh installs everything from fetching spack to PARCEL in one run. The arguments are the environment name (a directory under spack/stack/envs/), the installation directory and the number of parallel jobs.

bash spack/stack/install_stack.sh s86 $HOME/parcel_stack 16           # <env> <prefix> [jobs]
bash spack/stack/check_stack.sh $HOME/parcel_stack $HOME/parcel_check  # check on the login node
. $HOME/parcel_stack/setup.sh                                          # when using it
spack load parcel-sycl+mpi+cuda py-parcel-sycl+mpi+cuda
  • Built by spack: LLVM 18.1.8, AdaptiveCpp (hipsycl 24.10.0), OpenBLAS, binutils, Python 3.11 with NumPy, SciPy and pip, PARCEL itself, the C / Fortran API and the Python package.
  • Taken from each system: compilers, CUDA / ROCm and MPI. They are tied to the network and drivers of the machine, and are written as external packages in spack/stack/envs/<env>/spack.yaml.
  • spack itself (1.1.0.dev0) and the recipe collection (spack-packages) are pinned to the confirmed versions (at the top of install_stack.sh).
  • spack, its configuration and caches are all placed in the installation directory, and ~/.spack and /etc/spack are not read (SPACK_DISABLE_LOCAL_CONFIG=1). Existing spack environments neither affect it nor are affected.
  • The PARCEL source is the directory two levels above install_stack.sh (the top of the distribution package, which must contain Include/, capi/ and python/). To use another location, give PARCEL_SRC=<directory>.
  • envs/<env>/site_env.sh is read during the installation and when setup.sh is read (site modules for MPI, etc.). after_activate.sh is read after the environment is activated. compilers.yaml lists compilers installed before the main environment (to build a newer GCC on systems whose OS GCC is old).
  • If interrupted, rerun the same command to resume (installed packages are reused). With CONCRETIZE_ONLY=1, only concretization is performed.
  • check_stack.sh runs spack load for each installed configuration and checks that parcel can be imported from Python and that sample_c.c, sample_f.f90 and quick_start.cpp in examples/ build and find all libraries needed at run time (they are not run). The Fortran sample without MPI is compiled together with examples/sample_f_mpi_stub.f90.
  • The post-installation test is spack test run parcel-sycl py-parcel-sycl (results with spack test results). It builds and runs the Quick Start examples with the installed headers and libraries (parcel-sycl: C++, and C and Fortran with +capi; py-parcel-sycl: quick_start.py) and checks that the maximum relative error against the exact solution is at most 1e-6 (the same as “Checking After the Build”). Versions with MPI are started with MPIEXEC (default: bin/mpiexec of the MPI), MPIEXEC_NP_FLAG, MPI_NP (default 2) and MPIEXEC_ARGS. On a node without a GPU (a login node), the GPU versions only test the build and the runs are SKIPPED, so run the test on a GPU compute node as well. PARCEL_TEST_RUN=0 disables the runs. The number of threads and the decision on where it runs are the same as in “Checking After the Build” (if OMP_NUM_THREADS is not set, all available logical CPUs on a compute node and 4 on a login node; forced with QUICK_NODE), and the decision and the values used appear in the output of spack test results -l. For +fj +mpi (Fujitsu mpiexec), RC_ONLY=1 is the default (use RC_ONLY=0 to turn it off). With Intel MPI, the C and Fortran tests are built with the generic wrappers in the same place (mpicc, mpif90), and the underlying compiler is set to spack’s compiler (gfortran, etc.) with I_MPI_CC and I_MPI_F90 (and I_MPI_FC) (the mpiifx returned by spack calls ifx, which cannot read parcel_sycl_mod.mod built by gfortran). Run the GPU versions and +fj on compute nodes (a short batch job or an interactive job). The CPU versions may be run on a login node (follow the rules of the site).

4.9.6 Other Systems

On Linux systems other than the seven environments above, copy and edit the template spack/stack/envs/generic/, and install with install_stack.sh. The template follows the definitions for s86 and Miyabi-C. On Ubuntu 24.04 (WSL2; OS GCC 13.3.0, Open MPI 4.1.6, CUDA 12.6 from the NVIDIA repository, RTX A6000), it was edited as in the steps below and the eight configurations CPU and GPU (cuda_arch=86) × without and with MPI were installed; check_stack.sh, the Quick Start (C++, C, Python) and the verification sample (pcg, pgmres, ks_arnoldi) passed. On Rocky Linux 9.8 (compatible with RHEL 9; WSL2; OS GCC 11.5.0, Open MPI 4.1.1, CUDA 12.6 from the NVIDIA repository), the same eight configurations were installed and the same tests passed. Register the OS Open MPI of the RHEL family after putting it, including the headers, in one directory (“Registering MPI and CUDA”).

cp -r spack/stack/envs/generic spack/stack/envs/mysite           # copy and edit
CONCRETIZE_ONLY=1 bash spack/stack/install_stack.sh mysite $HOME/parcel_stack   # try concretization only
bash spack/stack/install_stack.sh mysite $HOME/parcel_stack 16                  # install

The places to edit are listed as steps in the comments at the top of spack.yaml.

  • The version and location of the compiler (GCC) (check with gcc --version and which gcc g++ gfortran).
  • To use MPI, uncomment the two +mpi lines of specs: and the mpi and openmpi lines of packages:, and edit the version and location (see “Generic Linux” for the format).
  • To use NVIDIA GPUs, uncomment the +cuda lines and the cuda lines, edit cuda_arch (found as in “Running on GPUs”) and the version and location of CUDA, and change the hipsycl and llvm lines for the GPU. For AMD GPUs, start from the PS-B definition psb (external ROCm).
  • If the CPU is not x86_64, edit targets of llvm (aarch64 for Arm).
  • On systems that load MPI etc. with modules, write module load in site_env.sh (module load mpi/openmpi-x86_64 for the OS Open MPI of the RHEL family; the site_env.sh of the template has an example). On systems with little memory, lower the number of concurrent compilations with PARCEL_STACK_JOBS.

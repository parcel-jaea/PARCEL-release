3 Installing a SYCL Compiler

SYCL PARCEL consists of header files only, and a SYCL-capable compiler is required to use it. In the v1.2 tests, AdaptiveCpp (formerly hipSYCL / Open SYCL) was used in all environments. AdaptiveCpp uses LLVM (clang) as its front end and can generate code for CPUs (OpenMP), NVIDIA GPUs (CUDA), and AMD GPUs (HIP) from a single source.

  • AdaptiveCpp: https://github.com/AdaptiveCpp/AdaptiveCpp
  • Installation instructions (official): https://github.com/AdaptiveCpp/AdaptiveCpp/blob/develop/doc/installing.md
  • spack: https://spack.readthedocs.io/

AdaptiveCpp can also be built from source, but in all test environments for this version it was installed with spack. The spack package name is hipsycl. Whether to use a spack environment (spack env), its name, and the spack installation directory are up to the user. The examples below write them as <spack environment name> and <spack installation directory> (the names used in the tests are shown in the table of each environment). When no spack environment is used, omit the spack env activate line and remove --add from spack install. The compiler driver is acpp, and the kind of code to generate is specified with --acpp-targets=.

The procedure in this chapter installs AdaptiveCpp into an existing spack. Alternatively, spack/stack/install_stack.sh in the distribution package installs everything from fetching spack through LLVM, AdaptiveCpp, OpenBLAS and Python to PARCEL itself and its C, Fortran and Python APIs into a new spack environment separated from any existing spack (MPI, CUDA / ROCm and compilers are taken from each system; “Installing with spack” in the Installation chapter). On macOS, spack is not used; AdaptiveCpp is installed with Homebrew (“macOS (Homebrew)”). The procedure for Linux systems other than the test environments is in “Generic Linux”, and how to install LAPACKE in “Installing LAPACKE”.

Example configurations of the environments used for testing are shown in the table at the beginning of each environment’s section below (see the Glossary for the names of environments and devices; the hardware column is the configuration of the compute nodes). Module versions and the like may change with site updates. AdaptiveCpp in all eight environments is the same commit 7677cf6e (24.10.0+git.7677cf6e.20241220).

When the login nodes and compute nodes have different CPU architectures (e.g., Odyssey), build both AdaptiveCpp and PARCEL on the compute nodes. In environments where the architectures match, building on the login node is fine. However, when -march=native is specified, make sure that the login node and compute nodes have the same CPU generation.

When the OpenMP backend is used with --acpp-targets=omp, the run-time thread-binding behavior depends on the version of the linked libomp. With the libomp of LLVM 18.1.8 (s86 CPU, PS-A), setting OMP_PROC_BIND causes all worker threads to be packed onto a single core, which results in a large slowdown. To avoid this, leave OMP_PROC_BIND unset or set it to false at run time (other values such as spread show the same problem). If the cores of each rank are assigned by the binding of mpirun (such as --bind-to core), the threads stay within that range.

3.2 Odyssey (Wisteria-Odyssey, A64FX)

Item Value
Hardware (CPU / GPU) A64FX (48 cores)
OS RHEL 8 (compute nodes)
Host compiler Fujitsu FCC tcsds-1.2.43 (fj/1.2.43, clang mode)
MPI Fujitsu MPI 1.2.43 (fjmpi/1.2.43)
CUDA / ROCm —
AdaptiveCpp 24.10.0 (~cuda)
LLVM (clang) 18.1.8 (spack, built with GCC 8.3.1)
Installation method (spack environment) spack, odyssey (built on compute nodes)
BLAS / LAPACK Fujitsu LAPACK (-lfjlapack)
--acpp-targets omp.library-only

The Odyssey compute nodes are A64FX (48 cores, 4 CMGs), whose architecture differs from that of the login nodes. Therefore, both the installation of AdaptiveCpp and the build of PARCEL are performed on the compute nodes (spack is run in a batch job or an interactive job).

On Odyssey, --acpp-targets=omp.library-only is used. In this mode, AdaptiveCpp acts only as the SYCL runtime library, and the entire code, including kernels, is compiled by the host C++ compiler. The Fujitsu compiler (FCC, clang mode) is specified as the host compiler with ACPP_CPU_CXX. This enables the optimization of the Fujitsu compiler for A64FX and the Fujitsu OpenMP runtime. However, AdaptiveCpp appends -O3 after ACPP_OMP_CXX_FLAGS, so -Kfast does not take effect. Fusion of multiply-adds into FMA is specified with -ffp-contract=fast on the command line, as in the Recommended Options. LLVM 18.1.8 was installed with spack and placed in the spack environment (odyssey in the tests). Fujitsu MPI (mpiFCC) is used for MPI, and Fujitsu LAPACK (-lfjlapack) for LAPACK.

Installation (once; on a compute node)

LLVM and AdaptiveCpp for A64FX are built on a compute node. The spack environment used in the tests is defined by the two specs llvm@18 and hipsycl %clang@18: LLVM 18.1.8 is built with the OS-bundled GCC 8.3.1, and AdaptiveCpp 24.10.0 (without CUDA; ~cuda is the default) is built with that clang. The following batch job creates the same installation (spack 1.1.0.dev0 was used).

When building on a compute node, take care of the parallelism, the memory limit and the processing time.

  • Parallelism: the -j option of spack install sets the number of concurrent compilations. With the default (the number of logical CPUs, 48 on A64FX) or -j32, the memory runs out while building LLVM. -j12 was used in the tests.
  • Memory limit: one A64FX node has 32 GiB of HBM2, of which about 28 GiB can be used by a user job. Compiling and linking LLVM takes much memory per process. With -j32, the peak reached about 29 GiB and the job stopped for lack of memory. In that case, lower -j and rerun the same command; installed packages are reused.
  • Processing time: one A64FX core is slower than an x86 core, and building LLVM 18.1.8 with -j12 took about 3 hours (1 h 30 min build, 1 h 25 min install). All dependencies including LLVM took about 4 hours 30 minutes. Allow a sufficient elapsed-time limit (elapse) and use a long resource group; elapse=24:00:00 was used in the tests. If the job stops at the limit, rerunning the same job continues the installation.
#!/bin/bash
#PJM -L "rscgrp=<resource group>"
#PJM -L "node=1"
#PJM -L "elapse=24:00:00"           # about 3 hours for LLVM with -j12; use a long resource group
#PJM -g <group>
#PJM -j

. /etc/profile.d/modules.sh
module purge
module load odyssey
JOBS=12                               # concurrent compilations; 32 or more runs out of memory (about 28 GiB) for LLVM
export SPACK_ROOT=<spack installation directory>
# (optional) place the spack user configuration and cache outside the home directory
export SPACK_USER_CONFIG_PATH=<spack user configuration directory>
export SPACK_USER_CACHE_PATH=<spack cache directory>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env create <spack environment name>      # first time only
spack env activate <spack environment name>
spack compiler find                  # registers the OS GCC 8.3.1 and others
spack install -j ${JOBS} --add llvm@18
spack install -j ${JOBS} --add hipsycl %clang@18

Settings for use

On Odyssey, the following settings are also made on a compute node (inside the job), as is the build.

. /etc/profile.d/modules.sh
module purge

export SPACK_ROOT=<spack installation directory>

OS RHEL 8.10 (login node)
Host compiler GCC 8.3.1 (gcc/8.3.1)
MPI Open MPI 4.1.1 (ompi/4.1.1, non-CUDA-aware build)
CUDA / ROCm CUDA 12.2 (cuda/12.2)
AdaptiveCpp 24.10.0 (+cuda)

Since llvm@13.0.1 and llvm@18.1.8 coexist in the spack environment, specify the version explicitly, as in spack location -i llvm@18. A CUDA-aware Open MPI is separately available as ompi-cuda/4.1.5-12.2.

The Aquarius compute nodes have Intel Xeon Platinum 8360Y (36 cores ×2) + NVIDIA A100-SXM4-40GB ×8. AdaptiveCpp (with the CUDA backend) and LLVM 18.1.8 were installed in the spack environment (aquarius in the tests), and CUDA 12.2 was used. The host compiler is the OS-bundled GCC 8.3.1. For OpenMPI, the site’s ompi module is used (the default at the time of the tests was 4.1.1, a non-CUDA-aware build), and spack’s hwloc is added to LD_LIBRARY_PATH.

Installation (once)

The spack environment used in the tests is defined by the two specs llvm@18 %gcc and hipsycl+cuda %clang@18: LLVM 18.1.8 is built with the OS-bundled GCC 8.3.1, and AdaptiveCpp 24.10.0 with the CUDA backend is built with that clang. The site CUDA 12.2 of the cuda module is used as a spack external package, and OS tools such as cmake, perl and python were also registered as externals. The following steps create the same installation (spack 1.1.0.dev0 was used).

. /etc/profile.d/modules.sh
module purge
module load aquarius
module load cuda
export SPACK_ROOT=<spack installation directory>
# (optional) place the spack user configuration and cache outside the home directory
export SPACK_USER_CONFIG_PATH=<spack user configuration directory>
export SPACK_USER_CACHE_PATH=<spack cache directory>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env create <spack environment name>      # first time only
spack env activate <spack environment name>
spack compiler find                  # registers the OS GCC 8.3.1 and others
spack external find                  # registers OS tools and the CUDA 12.2 of the cuda module as externals
spack install --add llvm@18 %gcc
spack install --add hipsycl+cuda %clang@18

Settings for use

. /etc/profile.d/modules.sh
module purge
module load aquarius
module load cuda
module load ompi
export SPACK_ROOT=<spack installation directory>
# (optional) place the spack user configuration and cache outside the home directory
export SPACK_USER_CONFIG_PATH=<spack user configuration directory>
export SPACK_USER_CACHE_PATH=<spack cache directory>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env activate <spack environment name>
export cuda_root=/work/opt/local/x86_64/cores/cuda/12.2
export sycl_root=`spack location -i hipsycl`
export llvm_root=`spack location -i llvm@18`
export hwloc_root=`spack location -i hwloc`
export ACPP_CUDA_PATH=$cuda_root
export LD_LIBRARY_PATH=$hwloc_root/lib:$sycl_root/lib/:$llvm_root/lib/:$cuda_root/lib64:${LD_LIBRARY_PATH}
export KMP_STACKSIZE=1G
export MPICXX_CXX=acpp
export OMPI_CXX=acpp

The spack hwloc ($hwloc_root/lib) is placed at the head of LD_LIBRARY_PATH to avoid a version mismatch of libraries. The site Open MPI 4.1.1 uses an old hwloc; if it is loaded first, the LLVM OpenMP runtime (libomp.so), built against a newer hwloc, fails to load and the CPU backend of AdaptiveCpp becomes unusable (runs with MPI stop even with builds for the GPU). Searching the spack hwloc first makes both use the newer hwloc. The spack recipe parcel-sycl makes the same setting at spack load (“Installing with spack” in “Installation”).

With OpenMPI 4.1 on Aquarius, the mpirun processes of jobs that start at the same time may compete for the session directory in /tmp and fail to start. In run jobs, give each job its own session directory before mpirun.

PARCEL_SESS=/tmp/parcel_${PJM_JOBID:-$$}
mkdir -p ${PARCEL_SESS}
export OMPI_MCA_orte_tmpdir_base=${PARCEL_SESS}
export OMPI_MCA_btl_vader_backing_directory=${PARCEL_SESS}
trap 'rm -rf ${PARCEL_SESS}' EXIT

  packages:

      externals:

        prefix: /work/opt/local/x86_64/cores/intel/2023.2.0

        prefix: /work/opt/local/x86_64/apps/gcc/11.4.1/ompi/4.1.6
      buildable: false
    hipsycl:
      require: '%oneapi'
. /etc/profile.d/modules.sh

export SPACK_ROOT=<spack installation directory>
. $SPACK_ROOT/share/spack/setup-env.sh

spack env activate <spack environment name>
spack compiler find                  # registers the OS GCC 11.4.1 and others

3.9 Generic Linux (RHEL Family, Ubuntu Family)

This section shows how to install AdaptiveCpp on Linux systems other than the test environments of this manual. There are two ways.

  • Install PARCEL together with its prerequisites: edit the template spack/stack/envs/generic/ of the distribution package and install with install_stack.sh (“Other Systems” in “Installation”).

3.9.2 Fetching and Configuring spack

spack 1.x is targeted (the version used by install_stack.sh is pinned at its top; the procedure of this section was confirmed with the development version 1.3.0.dev0 at the time of fetching). Fetch spack, create an environment, and register the compilers and the OS tools.

git clone -c feature.manyFiles=true https://github.com/spack/spack.git <spack installation directory>
export SPACK_ROOT=<spack installation directory>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env create <spack environment name>      # first time only
spack env activate <spack environment name>
spack compiler find                  # register GCC and other compilers found in PATH
spack external find                  # register OS tools such as cmake, perl and python as external packages

OS tools registered with spack external find are used without being built by spack, which shortens the installation.

3.9.3 Registering MPI and CUDA

MPI and CUDA are taken from the system and are not built by spack. spack external find openmpi cuda may find them, but on systems that provide them as modules they are often not found; write them directly into the definition of the spack environment (spack.yaml, opened with spack config edit). Adjust the versions and locations to your system.

spack:
  packages:
    mpi:
      require: [openmpi]
    openmpi:
      buildable: false
      externals:
      - spec: openmpi@4.1.6~cuda
        prefix: /path/to/openmpi/4.1.6     # one level above bin/mpicc
    cuda:
      buildable: false
      externals:
      - spec: cuda@12.6.20
        prefix: /path/to/cuda/12.6
  • buildable: false tells spack not to build the package itself and to use only the registered one.
  • Keep a single MPI in the environment. If several MPIs are registered as externals, an unintended configuration (a CUDA-aware build, etc.) may be chosen.
  • Register a CUDA version supported by the driver of the compute nodes or older (“Running on GPUs”).
  • Example for OS packages (Ubuntu 24.04): Open MPI 4.1.6 with prefix: /usr, and CUDA 12.6 from the NVIDIA repository with spec: cuda@12.6.85 and prefix: /usr/local/cuda-12.6. Find the versions with mpirun --version and nvcc --version.
  • Example for OS packages (Rocky Linux 9): Open MPI 4.1.1 (openmpi-devel) with spec: openmpi@4.1.1~cuda; CUDA is the same as on Ubuntu. The OS Open MPI of the RHEL family has bin/ and lib/ in /usr/lib64/openmpi and the headers in /usr/include/openmpi-x86_64. spack looks for the headers in include/ under prefix, so with prefix: /usr/lib64/openmpi the installation of packages depending on MPI (PARCEL with MPI) stops with Query of package 'openmpi' for 'headers' failed. Put them side by side in one directory as follows, and write that directory as prefix.
O=$HOME/openmpi-rhel                              # any location; the OS files are not changed
mkdir -p $O
ln -s /usr/lib64/openmpi/bin $O/bin
ln -s /usr/lib64/openmpi/lib $O/lib
ln -s /usr/lib64/openmpi/share $O/share
ln -s /usr/include/openmpi-x86_64 $O/include

3.9.4 Installing LLVM and AdaptiveCpp

Build LLVM 18 with the OS GCC, and build AdaptiveCpp (spack package hipsycl) with its clang. To use GPUs, select the backend with a variant.

spack install --add llvm@18 %gcc
spack install --add hipsycl %clang@18                              # CPU only
# spack install --add hipsycl+cuda %clang@18                       # also NVIDIA GPUs (instead of the above)
# spack install --add hipsycl+rocm amdgpu_target=gfx942 %clang@18  # also AMD GPUs (MI300A example)

Building LLVM takes a long time and much memory. The number of concurrent compilations is set with spack install -j <n>. If the build stops for lack of memory, lower the number and run the same command again (installed packages are reused; see the “Odyssey” section for an example on Odyssey).

3.9.5 Settings for Use

export SPACK_ROOT=<spack installation directory>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env activate <spack environment name>
export sycl_root=`spack location -i hipsycl`
export llvm_root=`spack location -i llvm@18`
export LD_LIBRARY_PATH=$sycl_root/lib:$llvm_root/lib:${LD_LIBRARY_PATH}
export ACPP_CUDA_PATH=<CUDA location>       # for NVIDIA GPUs
export OMPI_CXX=acpp MPICXX_CXX=acpp          # make the MPI wrapper (Open MPI) call acpp
  • The lib/ of LLVM is added to LD_LIBRARY_PATH because executables for the CPU use the LLVM OpenMP runtime (libomp.so). Alternatively, link with -Wl,-rpath,$llvm_root/lib (RPATH).
  • The OS Open MPI of the RHEL family is loaded with an environment module (module load mpi/openmpi-x86_64; until then mpicxx and mpirun are not in PATH).
  • The variable that makes the MPI compiler wrapper call acpp depends on the MPI: OMPI_CXX for Open MPI, MPICH_CXX for the MPICH family, and I_MPI_CXX for Intel MPI (see the “PS-A” section for an example on PS-A).
  • Find the location of LAPACKE and give it in the compile flags (“Installing LAPACKE”).

Check the installation by building and running the C++ program of the Quick Start. On GPUs, also check the name of the device used (“Running on GPUs”).

3.9.6 Windows WSL2

Linux on Windows WSL2 (Ubuntu, Rocky Linux) can also use the CPU and NVIDIA GPUs with the procedure of this section and with install_stack.sh (confirmed with Ubuntu 24.04 and Rocky Linux 9, using two RTX A6000). The differences from Linux systems follow.

  • Size of the virtual disk: the OS, CUDA and the installation directory of install_stack.sh used 20 to 30 GB. wsl --install places the disk on the system drive by default; if it has little free space, use wsl --install --location <dir>, or fetch an image for WSL from the distributor (the root file system of Ubuntu, Rocky-9-WSL-Base-<version>.x86_64.wsl of Rocky Linux, etc.) and place it on another drive with wsl --import <name> <dir> <file>.
  • Memory and CPUs: the limits used by WSL2 are set in %UserProfile%\.wslconfig on the Windows side (memory= and processors= in [wsl2]). Match the number of parallel jobs of the LLVM build to this memory (it installed with -j 16 and memory=24GB).
  • GPUs: install the driver on the Windows side, not inside WSL2. Install only the CUDA toolkit inside WSL2, from the apt repository of NVIDIA for WSL (wsl-ubuntu) (apt install cuda-toolkit-12-6, installed in /usr/local/cuda-12.6). The RHEL family (Rocky Linux 9) has no repository for WSL, so install cuda-toolkit-12-6 from the ordinary rhel9 repository (no driver package is installed, and the libcuda.so of WSL is used; the installation directory is the same). nvidia-smi and the driver libraries are in /usr/lib/wsl/lib, which is in PATH of ordinary shells but not of systemd services and the like.
  • Multiple GPUs: gpu_bind.sh (“Mapping One Rank to One Device”) assigns a different GPU to each rank. Without it, all ranks use the same GPU.
  • Long builds: WSL2 stops some time after all shells using the distribution have ended, and builds running inside stop too. Keep a terminal open while building, or leave a process such as wsl -d <name> -- sleep infinity running on the Windows side.

3.10 Installing LAPACKE

The eigenvalue solver ks_arnoldi of PARCEL uses LAPACKE (the C interface of LAPACK). All solvers are built by default, so the header lapacke.h and the library are needed even when only linear solvers are used (they are unnecessary if ks_arnoldi is excluded with -DPARCEL_ENABLE_KS_ARNOLDI=0; “Selecting the Solvers to Build”). Examples of installing it follow. Package names may differ between OS versions and additional repositories (such as CRB for the RHEL family). The RHEL family row was confirmed on Rocky Linux 9, and the Ubuntu family row on Ubuntu 24.04.

OS etc. Example
RHEL family dnf install openblas-devel (after enabling CRB; “Prerequisites”)
Ubuntu family apt install libopenblas-dev liblapacke-dev
macOS brew install openblas (“macOS (Homebrew)”)
spack spack install openblas (OpenBLAS includes LAPACKE)
Fujitsu environment (Odyssey) Nothing to install. The implementation is Fujitsu LAPACK (-lfjlapack, included in the Fujitsu language environment), and the header lapacke.h of the OS OpenBLAS is borrowed (see below)

Find the installed header and library as follows.

find / -name lapacke.h 2>/dev/null               # find the header
rpm -ql openblas-devel | grep -E 'lapacke.h|\.so$'   # RHEL family: files installed by the package
dpkg -L liblapacke-dev | grep -E 'lapacke.h|\.so$'   # Ubuntu family: files installed by the package
ldconfig -p | grep -E 'liblapacke|libopenblas'        # Ubuntu family: the .so of OpenBLAS is in another package, so look in the loader's list
ls $(spack location -i openblas)/include $(spack location -i openblas)/lib   # spack
  • If the header is /usr/include/openblas/lapacke.h, add -I/usr/include/openblas. If it is in a standard location such as /usr/include/lapacke.h, no -I is needed.
  • If OpenBLAS includes LAPACKE (such as the OpenBLAS of spack), -lopenblas alone is enough. If LAPACKE is a separate library (liblapacke.so), add both, as in -llapacke -lopenblas. For libraries outside the standard locations, also add -L<dir> and -Wl,-rpath,<dir>.
  • On Rocky Linux 9 (RHEL 9 family), openblas-devel puts the header at /usr/include/openblas/lapacke.h, and OpenBLAS (libopenblas.so) includes LAPACKE, so -I/usr/include/openblas -lopenblas (as in the Quick Start) is enough. lapack-devel is not needed (it would add another /usr/include/lapacke/lapacke.h and liblapacke.so).
  • On Ubuntu 24.04, libopenblas-dev and liblapacke-dev put the header at /usr/include/lapacke.h (no -I needed), and OpenBLAS does not include LAPACKE, so use -llapacke -lopenblas. With -lopenblas alone, linking a program that uses ks_arnoldi fails with LAPACKE_dgeev and others not found (programs that do not use it link, so this is easy to miss).
  • In an environment installed with install_stack.sh (a shell that has read setup.sh), use the OpenBLAS of spack (the include/ and lib/ of spack location -i openblas). setup.sh adds the lib/ of the view of the spack environment to LD_LIBRARY_PATH, so if you link with the OS LAPACKE, the OS BLAS loads the libopenblas.so.0 of spack and the run stops with symbol lookup error: ... undefined symbol: sgemv_thread_n or similar.
  • In the Fujitsu environment (Odyssey), give the header lapacke.h of the OS OpenBLAS (-I/usr/include/openblas) and Fujitsu LAPACK (-lfjlapack) as the implementation. Fujitsu LAPACK is in lib64/ of the Fujitsu language environment, so give that location with -L and -Wl,-rpath (for example, -L$fj_root/lib64 -Wl,-rpath,$fj_root/lib64 -lfjlapack; fj_root is defined in “Settings for use” of “Odyssey”). The whole build is in “Odyssey” of “Recommended Options” in “Installation”.
  • For the Python package, give the same values with the build settings LAPACKE_INCLUDE_DIR (directory of the header) and LAPACK_LIBS (link flags) (“Build Settings”).
  • With the spack recipe parcel-sycl, the recipe gives the location of OpenBLAS automatically.

Purpose and Overview

Today's computing environments use many kinds of hardware: GPUs, FPGAs and AI accelerators in addition to CPUs. These devices require different programming models (CUDA, OpenCL, etc.), which makes portability and maintenance of programs difficult. SYCL, an open standard defined by the Khronos Group, addresses this problem: it is based on C++ and enables single-source parallel programming on heterogeneous platforms including CPUs and GPUs.

The PARallel Computing ELements (PARCEL) library provides parallel Krylov subspace solvers suited to parallel computers whose computing performance is high but whose inter-node communication performance is relatively low. PARCEL had been developed separately for CPUs and NVIDIA GPUs; reimplementing it in SYCL improves performance portability and maintainability. v1.2 has been confirmed on Intel / Arm CPUs (including A64FX and Apple M4) and NVIDIA / AMD GPUs, and support for Intel GPUs, FPGAs and others is planned.

Because the performance and characteristics differ from hardware to hardware, choosing appropriate precisions (half, single, double, double-double) is important. SYCL PARCEL supports mixed-precision computation that flexibly combines different precisions depending on the algorithm and data, achieving fast and numerically stable solvers that keep the accuracy while reducing the cost of memory access.

Changes in v1.2

  • Eigenvalue solvers: power method (power), inverse power method (inverse_power) and the Krylov-Schur method (ks_arnoldi; nonsymmetric matrices and shift-invert).
  • An API that calls all seven solvers from C and Fortran, and the Python package parcel.
  • A single-process build without MPI (-DPARCEL_MPI=0).
  • spack recipes and a script that installs everything from fetching spack to PARCEL. On macOS, PARCEL can be installed with Homebrew.
  • Kernel optimizations for each environment (blocked reductions on CPUs, fully blocked kernels, gemv decomposition and ladder splitting of SpMV on A64FX, ladder splitting on AMD GPUs) and memory-saving defaults.
  • Verification of 13 precision configurations (combinations of half, single, double and double-double) for all solvers, regression tests (C++, C, Fortran, Python, with and without MPI) and performance tests.

Solvers

KindSolverProblem
Linear solverspcg: preconditioned conjugate gradient methodLinear systems with symmetric positive definite matrices; the lightest
pbicgstab: preconditioned stabilized biconjugate gradient methodLinear systems with nonsymmetric matrices, when each iteration should be light
pgmres: preconditioned generalized minimal residual methodLinear systems with nonsymmetric matrices, or symmetric but not positive definite ones, when stable convergence is wanted
pcagmres: preconditioned communication-avoiding generalized minimal residual methodThe same problems as pgmres, when many ranks make collective communication the bottleneck
Eigenvalue solverspower: power methodOne eigenvalue of largest magnitude
inverse_power: inverse power methodOne eigenvalue of smallest magnitude
ks_arnoldi: Krylov-Schur methodSeveral eigenvalues, complex conjugate pairs (nonsymmetric matrices), eigenvalues near a shift by shift-invert
PreconditionersPoint Jacobi preconditionerThe cheapest; small effect
Block Jacobi preconditionerFor CPUs; its effect depends on the numbers of ranks and blocks
Jacobi preconditionerFor GPUs; its effect does not depend on the partitioning

APIs for calling these solvers are provided for C++, C, Fortran and Python: C++ as a header-only library, C and Fortran as an API library, and Python as the package parcel (API Reference).

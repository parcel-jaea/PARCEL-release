4 インストール

　SYCL版PARCELの導入方法について説明する.
　PARCEL はヘッダーファイルのみで構成されている. ./Include/parcel_sycl.hpp をインクルードし, SYCL対応コンパイラでコンパイルすれば利用可能である. ライブラリとしての事前ビルドやインストール作業は不要である.

　ただし次の 3 点に注意する.

  • C++・C言語・Fortran では, 既定で MPI を使う (PARCEL_MPI の既定値 1). SYCL コンパイラ (acpp) を MPI のラッパ (mpicxx など) 経由で呼び出す. MPI を使わない 1 プロセス版は -DPARCEL_MPI=0 でビルドできる. Python と spack では既定が MPI なしである (「MPI の有無の既定」, 「MPI なしのビルド」).
  • 固有値ソルバ ks_arnoldi (Include/parcel_krylov_ks.hpp) は lapacke.h をインクルードし, LAPACKE を呼び出す. 既定では全ソルバが有効なので, 線形方程式だけを解く場合も LAPACKE のヘッダとライブラリを指定する. -DPARCEL_ENABLE_KS_ARNOLDI=0 で ks_arnoldi を外せば不要になる (「ビルドするソルバの取捨」).
  • ソース中の #include は相対パスで書かれている. サンプルプログラムは PARCEL のトップディレクトリでコンパイルする.

　SYCL対応コンパイラの導入は前章を参照のこと. spack で PARCEL ごと入れる方法は「spack によるインストール」に, Python のパッケージは「Python のパッケージ」に示す.

4.2 ビルド後の確認

　ビルド後の確認には bash examples/run_quick_checks.sh を使う. クイックスタートの 4 つの例 (C++・C言語・Fortran・Python) を examples/build_examples.sh でビルドして 1 プロセスで実行し, MPI ありのビルドでは C++ の例を 2 プロセスでも実行する. 各例は厳密解との最大相対誤差が 1e-6 以下なら check: ... PASS を表示する (「プログラムの概要」). 最後に PASS n / FAIL m (SKIP k) と所要時間を 1 行で表示し, 不合格が無ければ終了コード 0 で終わる. Python の例は, parcel (と NumPy・SciPy) を import できなければ SKIP とする (不合格にしない).

　ビルド (build_examples.sh quick) は SYCL のコンパイル (C++ の例と C言語・Fortran の API のラッパ) を同時に走らせる (同時に走らせる数は BUILD_JOBS. 既定は対象の数とコア数の小さい方). ビルドに成功すると, ビルドの設定 (SYCL_TARGET, CXXFLAGS, PARCEL_MPI, コンパイラとその場所など) とソース (ヘッダ, API, 例) の cksum を examples/build/build_stamp.txt に記録する. 2 回目からは, 実行ファイルがそろい記録が今と同じならビルドを飛ばして実行だけをする (1 分かからない). 設定かソースが変わっていれば, 違う項目を表示して作り直す. --rebuild を付けると必ず作り直す.

export OMPI_CXX=acpp
bash examples/run_quick_checks.sh                 # MPI あり. 最後の行: === PASS 6 / FAIL 0 (SKIP 0)  所要 <秒> s
PARCEL_MPI=0 bash examples/run_quick_checks.sh    # MPI なし
bash examples/run_quick_checks.sh --rebuild       # 作り直す
NO_BUILD=1 bash examples/run_quick_checks.sh      # 記録を見ずに examples/build/ を実行だけする

　コンパイラ・ターゲット・LAPACK の環境変数は build_examples.sh と同じである (GPU は例えば SYCL_TARGET=--acpp-targets=cuda:sm_70). MPI の起動コマンドは MPIEXEC (既定 mpirun), MPIEXEC_NP_FLAG (既定 -n), MPI_NP (既定 2), MPIEXEC_ARGS で変える. 起動コマンドを通さないと MPI_Init できない MPI (富士通 MPI など) では MPIEXEC_ALL=1 で 1 プロセスの実行も起動コマンドを通す. 富士通の mpiexec はランクの標準出力をジョブのログに出し, check の行を読めないので, 富士通の mpiexec (MPIEXEC=mpiexec で, その実体が /opt/FJSV… にあるもの) では RC_ONLY=1 (終了コード 0 なら合格) が既定になる (外すときは RC_ONLY=0). spack で入れた場合は spack test run parcel-sycl py-parcel-sycl が同じ判定を行う (「spack によるインストール」).

　スレッド数と実行場所. OMP_NUM_THREADS が未設定なら, 計算ノード (ジョブの中) では使える論理 CPU 数をすべて, ログインノードでは 4 (使える数が 4 未満ならその数) を使う. MPI の実行では合計がそれになるようプロセス数で割る (最低 1. ログインノードで 2 プロセスなら 1 プロセス 2 スレッド). 使える論理 CPU 数は, CPU の割り当て (nproc)・cgroup の CPU の上限・ジョブのこのノードの割り当て (PBS の NCPUS, Slurm の SLURM_CPUS_ON_NODE) の最も小さいものである. 計算ノードかどうかはジョブの環境変数 (PBS の PBS_JOBID, 富士通 PJM の PJM_JOBID, Slurm の SLURM_JOB_ID) の有無で決め, QUICK_NODE=compute / QUICK_NODE=login で強制できる. 判定と使った値は最初に表示する. OMP_NUM_THREADS を設定していればその値を使う (ジョブではスケジューラが設定していることがある. PBS の ompthreads (キューの既定が 1 のことがある), 富士通 PJM の --omp thread=). Open MPI で MPIEXEC_ARGS に配置の指定 (--bind-to, --map-by) が無ければ --bind-to none を足す (Open MPI は 2 プロセス以下だと各プロセスを 1 コアに固定し, 複数のスレッドが 1 コアに詰め込まれるため).

　どこで流すか. CPU の環境はログインノードでもよい (施設の規則に従う). GPU の環境と A64FX (Odyssey) は計算ノード (短いバッチジョブか対話ジョブ) で流す (ログインノードには GPU が無く, A64FX の実行ファイルは x86 のログインノードでは動かない). GPU の環境で MPI の試験 (2 プロセス) を流すとき, このスクリプトはプロセスごとに GPU を 1 台ずつ割り当てる設定 (「1 ランクと 1 デバイスの対応」 の gpu_bind.sh のようなもの) をしないので, 2 プロセスが同じ GPU を使うことがある.

4.4 マクロ

　PARCEL はヘッダーファイルだけのライブラリなので, 利用者のプログラムをコンパイルするときに-D<マクロ>または-D<マクロ>=<値>を付けると, ライブラリ本体 (Include/) の構成や動作を選べる. どのマクロも既定値のままで使え, 通常は何も指定しなくてよい. 目的ごとに次の 4 種類がある.

  • ビルドするソルバの取捨: 使わないソルバを外して, コンパイル時間を短くする
  • 整数型: 大域の添字 (既定 64 ビット) とランク内の添字 (既定 32 ビット) の幅を選ぶ
  • 最適化: 環境に合わせて演算カーネルのループ構造を選ぶ. また, 既定ではメモリを少なくする設定になっているので, メモリを使って速くする最適化オプションを選ぶ (最適化)
  • 検査と数値演算: 誤った結果を防ぐための検査と, double-double の演算の方式を選ぶ (既定のまま使う. 検査と数値演算)

　このほかに診断・切り分け用のマクロがあるが, 通常は指定しない.

4.4.1 ビルドするソルバの取捨 (Include/parcel_solver_select.hpp)

　既定では全ソルバが有効であり, 通常は何も指定しなくてよい. 1 つの翻訳単位に全ソルバが入るためコンパイル時間が長く (A64FX では 1 構成 6〜14 分), 切り分けなどで使うソルバが決まっている場合に外すと短縮できる.

　各マクロは 1 でそのソルバを入れ, 0 で外す. 各ソルバのマクロを指定しなければPARCEL_ENABLE_ALL_SOLVERSの値 (既定 1) になるので, 何も指定しなければ全ソルバが入る. 一部のソルバだけを入れる場合はPARCEL_ENABLE_ALL_SOLVERS=0としてから, 入れるソルバを 1 にする.

マクロ 既定値 説明
PARCEL_ENABLE_ALL_SOLVERS 1 下記の各ソルバのマクロを指定しなかったときの値. 0 にすると, 1 を指定したソルバだけが入る
PARCEL_ENABLE_PCG 1 (PARCEL_ENABLE_ALL_SOLVERS の値) parcel::krylov::pcg
PARCEL_ENABLE_PBICGSTAB 1 (PARCEL_ENABLE_ALL_SOLVERS の値) parcel::krylov::pbicgstab
PARCEL_ENABLE_PGMRES 1 (PARCEL_ENABLE_ALL_SOLVERS の値) parcel::krylov::pgmres
PARCEL_ENABLE_PCAGMRES 1 (PARCEL_ENABLE_ALL_SOLVERS の値) parcel::krylov::pcagmres (QQを作らない方式CAGMRES_Q_IMPLICITを含む)
PARCEL_ENABLE_POWER 1 (PARCEL_ENABLE_ALL_SOLVERS の値) parcel::krylov::power
PARCEL_ENABLE_INVERSE_POWER 1 (PARCEL_ENABLE_ALL_SOLVERS の値) parcel::krylov::inverse_power
PARCEL_ENABLE_KS_ARNOLDI 1 (PARCEL_ENABLE_ALL_SOLVERS の値) parcel::krylov::ks_arnoldi. 0 にすると LAPACKE は不要になる (検証用サンプルを除く)

　依存関係は自動で補われる. inverse_power を有効にすると pcg と pgmres が, ks_arnoldi を有効にすると pgmres が有効になる. 1 つも有効でない場合はコンパイルエラーになる. PARCEL_ENABLE_CHOLQR_PCAGMRES というマクロは無く, 指定するとコンパイルエラー (#error) になる.

# pgmres だけを入れる (他はすべて外す)
-DPARCEL_ENABLE_ALL_SOLVERS=0 -DPARCEL_ENABLE_PGMRES=1
# ks_arnoldi だけを外す (他はすべて入れる)
-DPARCEL_ENABLE_KS_ARNOLDI=0

4.4.2 整数型

　行番号・列番号・行数・非零要素数などの整数は, 大域の添字をマクロPARCEL_INTの型で, 1 つのランクの中の添字 (デバイス上の CRS など) をマクロPARCEL_LINTの型で持つ. 既定はPARCEL_INTが 64 ビット (int64_t. MPI の通信ではMPI_INT64_T), PARCEL_LINTが 32 ビット (int32_t, MPI_INT32_T) である. この既定にした理由 (大規模な問題での桁あふれと局所カーネルの速さ) は基本構成の「整数型」に示す.

指定 PARCEL_INT PARCEL_LINT 備考
なし (既定) int64_t int32_t
-DPARCEL_LOCAL_INT64 int64_t int64_t -DPARCEL_LOCAL_INT64=0は既定と同じ
-DPARCEL_INT32 int32_t int32_t -DPARCEL_INT32=0は既定と同じ
-DPARCEL_INT int64_t int32_t PARCEL_INTを 64 ビットにする旧来の書き方. 互換のため受け付ける (値は見ない)
-DPARCEL_INTと-DPARCEL_INT32の両方 — — 矛盾するので#errorでビルドを止める
-DPARCEL_INT32と-DPARCEL_LOCAL_INT64の両方 — — ランク内の型が大域の型より広くなるので#errorでビルドを止める

　選ばれた幅はマクロPARCEL_INT_BITSとPARCEL_LINT_BITS (いずれも 64 または 32) で分かる.

　型の選び方 (扱える行列の範囲, 大規模な問題での桁あふれ, メモリ量と局所カーネルの速さへの影響, C言語・Fortran の API との関係) は基本構成の「整数型」に示す.

4.4.3 最適化

　計算 (アルゴリズムと反復回数) を変えずに速さを上げる最適化のマクロを示す. 演算カーネルのループの形を選ぶもの (前半の 8 つ) と, メモリを使って速くするもの (後半の 2 つ. 最適化オプション) がある. 各最適化の仕組み, 効果, 環境ごとの既定は「最適化」の章に, 環境ごとのコンパイルコマンドは推奨オプションに示す. 既定はメモリを少なくする設定である.

マクロ 既定値 説明
_BLOCKING_LOOP_ 0 1 で SpMV 以外の全カーネル (内積, axpy, 前処理など) をブロック化版に替える (ブロック化). A64FX 向け
_BLOCKING_LOOP_DOT_ 0 1 で縮約 (dot,dddot,max) だけをブロック化版に替える. A64FX 以外の CPU 向け. GPU では指定しない
PARCEL_SPMV_LADDER 0 1 で SpMV の内側ループを梯子状に分割する (梯子分割). AMD の GPU と A64FX 向け. NVIDIA の GPU には付けない
PARCEL_PRECON_LADDER 0 (PARCEL_SPMV_LADDER の値) Jacobi 前処理の反復ループの梯子分割. A64FX では 0 を明示する
PARCEL_GEMV_AS_AXPY 0 (_BLOCKING_LOOP_ の値) 1 で gemv を M 回の axpy に分解する (gemv の分解). 丸めの順序が変わる
PARCEL_A64FX_AXPY_C 1 1 で, 係数を値で渡す axpy と gemv の axpy 分解版を A64FX 向けに書き直した版を使う (A64FX 向けの最適化の C). 0 で書き直す前の形にする. 結果は変わらない. _BLOCKING_LOOP_のビルドでだけ働く
PARCEL_CG_FUSED 0 (_BLOCKING_LOOP_ の値) 1 でpcgの 1 反復のカーネルを融合する (xx と pp の更新, rr の更新と ⟨r,r⟩\langle r, r \rangle. A64FX 向けの最適化の D). 結果は変わらない. _BLOCKING_LOOP_のビルドでだけ 1 にできる
PARCEL_JACOBI_NODIV_UNIT 1 1 で Jacobi 前処理の右辺の準備で割る値が 1 のとき割り算を省く (A64FX 向けの最適化の E). 結果は変わらない. _BLOCKING_LOOP_のビルドでだけ働く
PARCEL_JACOBI_ROW2 0 (_BLOCKING_LOOP_ の値. PARCEL_PRECON_LADDERが 1 なら 0) 1 で前処理行列が単精度のとき Jacobi 前処理の反復を 2 行ずつ交互に処理する (A64FX 向けの最適化の F). 結果は変わらない. 倍精度の前処理行列とその場で計算する版では使わない
PARCEL_JACOBI_ONTHEFLY 1 (A64FX 向けでは 0) Jacobi 前処理 (PRECON_JACOBI) のB=DA−1RB = D_A^{-1}Rの値を持たず, 適用のたびにAAの値とDA−1D_A^{-1}から計算する. 0 で値を保持する (最適化オプション「H なし」. AAの非零の数 × 前処理行列の精度の大きさのメモリを使う). 行列スケーリング有効時, 係数行列・前処理行列・前処理の演算精度のいずれかが double-double の場合は 1 でも値を保持する. _BLOCKING_LOOP_ (または _BLOCKING_LOOP_SPMV_) が 1 の A64FX 向けのビルドでは既定が 0 になる (「メモリと速さの選択」)
PARCEL_PCG_NO_XHIST 1 pcgが解の更新をまとめる反復数 (pstep) の既定. 1 で 1 (探索方向を 1 本だけ持ち, 毎反復更新),0 で 4 (最適化オプション「G なし」. 袖付きベクトル 3 本分のメモリを使う). 実行時の環境変数PARCEL_PSTEPが優先する

4.4.4 ks_arnoldi の直交化の既定

　ks_arnoldiの Arnoldi 過程の直交化 (固有値ソルバの章の Krylov-Schur 法) は, プログラムでset_qr_algo()を呼んで選ぶ (API リファレンスのks_arnoldiのset_qr_algo()). 呼ばないときの既定は, 次のマクロでビルド時に選ぶ. 環境変数PARCEL_KS_ORTHOは読まない (設定されていると, 最初のsolver()で rank 0 が標準エラーに警告を 1 行出す. 動作は変わらない).

マクロ 既定値 説明
PARCEL_KS_ORTHO_DEFAULT 未定義 (cgs2) cgs2 (古典 Gram-Schmidt 法 2 回) または mgs (修正 Gram-Schmidt 法 2 回). PS-A 向けのビルド (spack の環境psa, バリアントks_ortho=mgs) はmgsである. 未定義なら CGS2 (QR_CGS). set_qr_algo()で指定した値が優先する

4.4.5 検査と数値演算

　誤った結果を防ぐための検査と, double-double の演算の方式を選ぶ. 既定のまま使う. 外すと誤った結果を黙って返しうるので, 理由を理解したうえでのみ指定する.

マクロ 既定値 説明
PARCEL_REQUIRE_IN_ORDER 1 set_crsMat() と各ソルバの solver() の入口で, SYCL キューが in-order であることを検査し, 違反 (キューが無い場合を含む) は std::invalid_argument を投げる. PARCEL はカーネルを sycl::event や depends_on を使わずに 1 本のキューへ順に投入し, 前のカーネルの結果を次のカーネルが読むので, in-order 実行が前提である. SYCL 2020 の既定 (out-of-order) キューでは, accessor を使わない USM カーネル同士の実行順は保証されない. 0 で検査を外す
PARCEL_NO_CRS_CHECK 0 1 で set_crsMat() (通常版と double-double の hi/lo 版) の入力の検査を外す. 検査するのは, 局所行数 n が nend-nstart+1 に等しく 1 行以上であること (0 行のランクは扱えない), rowptr[0] == 0・単調非減少・rowptr[n] == nnz であること, 全ランクの行ブロックが全体の行を隙間・重複なく覆うこと (ランクの並び順は問わない), 列番号が全体の行数の範囲にあること. 非 MPI 版は rowptr と列番号だけを調べる. 崩れていれば全ランクが同じ std::invalid_argument を投げる (文言に崩れていたランクと内容). 費用は非零要素の走査 1 回と集団通信 2 回である. 外して崩れた入力を与えると, 袖通信の未初期化の受信バッファを使って黙って誤った結果になるか, 配列の範囲外を読む
PARCEL_ALLOW_FAST_MATH 未定義 定義すると -ffast-math / -ffinite-math-only (__FAST_MATH__ / __FINITE_MATH_ONLY__) 付きのビルドを許す. 既定では parcel_sycl.hpp が #error で止める. 結合則による式の書き換えで double-double の誤差項が消え, dd が黙って倍精度に落ちる. また NaN / Inf の検査 (std::isfinite) が消され, DIVERGED_NANORINF が働かなくなる. 定義した場合, dd の精度と NaN の検出は保証しない
PARCEL_DD_NO_FMA 未定義 定義すると double-double の積の誤差なし変換 (TwoProd) を, 既定の fma によるもの (p=fma(a,b,0)p = \mathrm{fma}(a,b,0), e=fma(a,b,−p)e = \mathrm{fma}(a,b,-p)) から Dekker の分割に替える. FMA 命令を持たない CPU 向けである. GPU (CUDA) では Dekker の分割が壊れるので使わない

　-fno-exceptions も使わない. 引数の検査 (std::invalid_argument など) と両立しない.

4.5.3 Odyssey

　A64FX ではログインノードと計算ノードのアーキテクチャが異なるため, 計算ノードでビルドする. ビルド用のジョブスクリプトの例を示す. MPI ラッパは mpiFCC を用い, OMPI_CXX=acpp で acpp を呼ばせる. acpp は omp.library-only ターゲットで ACPP_CPU_CXX の富士通コンパイラをホストコンパイラとして用いる. LAPACKE のヘッダの場所は他の環境と同じく -I/usr/include/openblas で指定し (この指定で計算ノードでビルドできる), 実装は富士通の libfjlapack を用いる.

#!/bin/bash
#PJM -L "rscgrp=short-o"
#PJM -L "node=1"
#PJM -L "elapse=2:00:00"
#PJM -g <グループ>
#PJM --omp thread=48
#PJM -j

# 環境設定: 「SYCL対応コンパイラのインストール方法」の章の「Odyssey」の「使用時の設定」を行う

cd ${PJM_O_WORKDIR}
LINKOPT="-L$fj_root/lib64 -Wl,-rpath,$fj_root/lib64 \
  -L$sycl_root/lib -Wl,-rpath,$sycl_root/lib \
  -L$llvm_root/lib -Wl,-rpath,$llvm_root/lib -lfjlapack"

mpiFCC -O3 -std=c++17 --acpp-targets=omp.library-only \
  -D_BLOCKING_LOOP_=1 -DPARCEL_SPMV_LADDER=1 -DPARCEL_PRECON_LADDER=0 \
  -ffp-contract=fast \
  -I/usr/include/openblas \
  -o verify_double tests/verify/parcel_krylov_sample_verify.cpp ${LINKOPT}

　1 回のビルドは Xeon より長くかかり, メモリも数 GiB を要する. 1 ノードのジョブが使えるメモリは 28 GiB なので, 複数の精度構成を同時にビルドする場合は本数を制限する.

　-ffp-contract=fastは積和 (a×b+ca \times b + c) を FMA 命令にまとめさせる. 富士通コンパイラの clang モードは既定では積和をまとめない. AdaptiveCpp はACPP_OMP_CXX_FLAGSの後ろにコマンドラインの-O3を並べて富士通コンパイラに渡すので, ACPP_OMP_CXX_FLAGSの-Kfastは後ろの-O3で打ち消され, 効かない. -Kfastを後ろに-O3を置かずに渡すなどして fast-math を効かせると, double-double と NaN の検出が壊れるため, PARCEL はビルドを#errorで止める (「-ffast-math を使わない」). -ffp-contract=fastはコマンドラインに置けば富士通コンパイラまで届く. Odyssey の 1 ノード (4 ランク × 12 スレッド, NX=256, pcg + Jacobi 前処理) で, 1 反復が 3 % 速くなった (SpMV は 10 %, axpy の本体は 25 %). 反復回数は変わらず, 結果は最後の桁が変わる (残差で相対 1e-11 程度). FMA は積を丸めずに和を取るので, 付けないビルドとはビット単位では一致しない. 結果をそろえたい場合は-ffp-contract=offにする. double-double の関数の中はInclude/ddlib.hppが FMA を禁じたままである (この節の最後の段落).

　A64FX 向けのビルド (-D_BLOCKING_LOOP_=1) では, Jacobi 前処理のBBの値を保持する (「メモリと速さの選択」の「H なし」) のが既定である (PARCEL_JACOBI_ONTHEFLYの既定 0. 指定は要らない). A64FX ではその場の計算 (非零ごとの掛け算と対角の判定) が前処理の時間に表れ, Odyssey の 1 ノード (NX=256, pcg + Jacobi 前処理) で値を保持すると前処理の区間が 0.77 倍, 収束までの総時間が 0.81 倍になる. そのかわりメモリがAAの非零 1 個あたり前処理行列の精度の大きさ (倍精度で 8 バイト) 増える. メモリを減らしたい場合は-DPARCEL_JACOBI_ONTHEFLY=1を明示する.

　実行時には, OpenMP のスレッドを待ち合わせの間も休ませないOMP_WAIT_POLICY=ACTIVEとKMP_BLOCKTIME=infiniteを設定する (推奨. ライブラリの既定ではないので, ジョブの環境で設定する). Odyssey の 1 ノード (4 ランク × 12 スレッド, 1 CMG に 1 ランク) で, 問題の大きさによらない 1 反復の固定費が 5.2 ms から 3.0 ms に減る. 装置あたりの行数が少ない場合に効く. 待っているスレッドもコアを使い続けるので, コアを取り合う配置 (1 ノードに他のプロセスを同居させるなど) では逆効果になる. このビルドで有効になる axpy の書き直しとpcgのカーネルの融合とあわせて, 効果と注意は「A64FX 向けの最適化」に示す.

　2026-10-10 より前のコードでは, double-double の演算のための FMA の禁止 (#pragma clang fp contract(off)) が富士通コンパイラではddlib.hppの範囲で戻らず, 以降の全カーネルで FMA 命令が使われていなかった (富士通コンパイラの clang モードはfloat_controlの push / pop を知らない). 今のコードは禁止を double-double の関数の中に限り, 他のカーネルではコンパイラの指定 (上の-ffp-contract=fast) どおり FMA を使う. 倍精度などの結果は以前のビルドと最後の桁で変わる.

4.5.9 C言語・Fortran のプログラム

　C言語・Fortran の API を使うプログラムは, ラッパ capi/wrapper_parcel_sycl.cpp を上の各環境のmpicxxのコマンドと同じフラグ (--acpp-targets, カーネル最適化, LAPACKE) でコンパイルし, C・Fortran の main と SYCL 対応コンパイラでリンクする. --acpp-targets はラッパのコンパイルとリンクでそろえる. acpp (clang) は PIE としてリンクするので, gcc・gfortran で作るオブジェクトには -fPIE を付ける. s86 CPU (Open MPI) の例を示す. 他の環境では 1 行目のフラグをその環境のものに替える.

# 環境設定: 「SYCL対応コンパイラのインストール方法」の章の「s86」の「使用時の設定」を行う
FLAGS="-O3 --acpp-targets=omp -march=native -mtune=native -D_BLOCKING_LOOP_DOT_=1"
mpicxx ${FLAGS} -I/usr/include/openblas -c capi/wrapper_parcel_sycl.cpp -o wrapper_parcel_sycl.o

# C言語
mpicc  -O2 -fPIE -Icapi -c prog.c -o prog.o
mpicxx --acpp-targets=omp -o prog prog.o wrapper_parcel_sycl.o -lopenblas -lm

# Fortran (PARCEL のモジュールを先にコンパイルする)
mpif90 -O2 -fPIE -c capi/parcel_sycl_mod.f90 -o parcel_sycl_mod.o
mpif90 -O2 -fPIE -c prog.f90 -o prog.o
mpicxx --acpp-targets=omp -o prog prog.o parcel_sycl_mod.o wrapper_parcel_sycl.o \
       $(mpif90 --showme:link) -L$(dirname $(mpif90 -print-file-name=libgfortran.so)) -lgfortran -lopenblas
  • リンクに加える MPI の Fortran ライブラリは MPI のラッパから調べる (Open MPI は mpif90 --showme:link, Intel MPI は mpif90 -show).
  • PS-A と PS-B では, LAPACKE の指定 (-I と -l:libopenblaso.so.0) を上の各節と同じにする. PS-A の Intel MPI では Fortran のラッパに mpif90 (中身は gfortran) を使う.
  • 富士通 Fortran (frt, mpifrt) と富士通 C (fcc, mpifcc) では -Kopenmp を付ける (使用方法の Fortran).
  • examples/build_examples.sh が同じ手順で examples/ のサンプルを作る. コンパイラ・ターゲット・LAPACK は環境変数で変える (SYCL_TARGET, CXXFLAGS, LAPACK_INC, LAPACK_LIB, MPICXX・MPICC・MPIFC, FC_LINK).

4.5.10 macOS (Homebrew)

　Homebrew で入れた環境 (「SYCL対応コンパイラのインストール方法」の「macOS (Homebrew)」) では, --acpp-targets=omp.library-only と縮約だけのブロック化 (-D_BLOCKING_LOOP_DOT_=1. 他の CPU と同じ) を用い, LAPACKE は Homebrew の OpenBLAS を指定する. Homebrew の AdaptiveCpp では--acpp-targets=ompも同じコンパイルになる. -march=nativeは要らない (付けても速さは同じ). 実行時は mpirun -n <並列数> --bind-to none で起動する. 次の例は クイックスタートの 4 言語のプログラムで確かめた.

eval "$(/opt/homebrew/bin/brew shellenv)"
export OMPI_CXX=acpp
B=/opt/homebrew
T="--acpp-targets=omp.library-only"
LAPACK_INC="-I$B/opt/openblas/include"
LAPACK_LIB="-L$B/opt/openblas/lib -lopenblas -Wl,-rpath,$B/opt/openblas/lib"
FC_RT="-L$B/opt/gcc/lib/gcc/current -lgfortran -Wl,-rpath,$B/opt/gcc/lib/gcc/current"

# C++ (MPI あり. MPI なしは mpicxx を acpp に替え -DPARCEL_MPI=0 を付ける)
mpicxx -O3 $T -D_BLOCKING_LOOP_DOT_=1 ${LAPACK_INC} \
  -o verify_double tests/verify/parcel_krylov_sample_verify.cpp ${LAPACK_LIB}

# C言語・Fortran (MPI あり)
mpicxx -O3 $T -D_BLOCKING_LOOP_DOT_=1 ${LAPACK_INC} -c capi/wrapper_parcel_sycl.cpp -o wrapper_parcel_sycl.o
mpicc  -O2 -Icapi -c prog.c -o prog_c.o
mpicxx $T -o prog_c prog_c.o wrapper_parcel_sycl.o ${LAPACK_LIB}
mpif90 -O2 -c capi/parcel_sycl_mod.f90 -o parcel_sycl_mod.o
mpif90 -O2 -c prog.f90 -o prog_f.o
mpicxx $T -o prog_f prog_f.o parcel_sycl_mod.o wrapper_parcel_sycl.o $(mpif90 --showme:link) ${FC_RT} ${LAPACK_LIB}
mpirun -n 4 --bind-to none ./prog_c

　macOS の gfortran の実行時ライブラリは .dylib なので, 場所 ($B/opt/gcc/lib/gcc/current) を-Lと-Wl,-rpathで与える. python/envs/mac_brew.sh を読み込むと, 同じ値が環境変数 (SYCL_TARGET, CXXFLAGS, LAPACK_INC, LAPACK_LIB, FC_LINK) に入り, examples/build_examples.sh でサンプルを作れる. Python のパッケージは「Python のパッケージ」に示す.

4.6 MPI の有無の既定

　PARCEL を MPI ありでビルドするか, MPI なしの 1 プロセス版でビルドするかは, マクロ PARCEL_MPI (1: あり, 0: なし) で決まる. 既定は使い方によって次のように異なる.

使い方 PARCEL_MPIの既定 決めている場所 MPI なし / ありにする指定
C++ (Include/parcel_sycl.hppをインクルード) 1 (MPI あり) Include/のヘッダ -DPARCEL_MPI=0を付ける
C言語 (capi/parcel_sycl_c.h) 1 (MPI あり) parcel_sycl_c.hとラッパ ラッパと main の両方に-DPARCEL_MPI=0を付ける
Fortran (capi/parcel_sycl_mod.f90) 1 (MPI あり) ラッパ (モジュールは MPI の有無によらない) ラッパに-DPARCEL_MPI=0を付け, use mpiを代用モジュールで満たす
examples/build_examples.sh 1 (MPI あり) 環境変数PARCEL_MPI PARCEL_MPI=0 bash examples/build_examples.sh
Python (python/. pip) 0 (MPI なし) python/CMakeLists.txt -C cmake.define.PARCEL_MPI=1で MPI あり
spack (parcel-sycl, py-parcel-sycl) 0 (MPI なし. バリアント~mpi) レシピのバリアントmpi +mpiで MPI あり

　C++・C言語・Fortran の既定が MPI ありなのは, v1.0 と同じ使い方 (MPI のラッパでコンパイルしmpirunで起動する) のプログラムをそのまま動かすためである. Python と spack の既定が MPI なしなのは, MPI の無い環境 (手元の計算機, macOS など) でもすぐに入れて試せるようにするためである. MPI ありの版を使う場合は, 上の指定で明示する. C言語・Fortran では, ラッパと main で指定が食い違うとコミュニケータの引数の型が合わず, 正しく動かない (リンクでは検出されない) ので, 両方を同じ指定でビルドする. C++ はヘッダだけのライブラリなので, 利用者のプログラムの指定がそのまま使われる. どちらの版も計算は同じで, MPI ありの版を 1 プロセスで実行した結果と MPI なしの版の結果はビット単位で一致する.

4.7 MPI なしのビルド

　-DPARCEL_MPI=0 を付けると, MPI を使わない 1 プロセス版をビルドできる. mpi.h を読まず, MPI のライブラリもリンクしないので, MPI のコンパイララッパ (mpicxx) ではなく SYCL 対応コンパイラ (acpp など) で直接コンパイルし, mpirun を使わずに実行する. 指定しない場合 (既定) は MPI ありである. 計算は MPI ありのビルドを 1 プロセスで実行した場合と同じで, 結果はビット単位で一致する.

acpp -O3 --acpp-targets=omp -march=native -DPARCEL_MPI=0 \
  -I/usr/include/openblas -o quick_start examples/quick_start.cpp -lopenblas
./quick_start

# examples/ の 4 本 (C言語・Fortran は gcc・gfortran でコンパイルする)
PARCEL_MPI=0 bash examples/build_examples.sh

　C言語・Fortran のプログラムを手でビルドする場合は, ラッパと C の main の両方に-DPARCEL_MPI=0を付け, MPI のラッパ (mpicxx, mpicc, mpif90) の代わりに acpp, gcc, gfortran を使う. Fortran のuse mpiは 1 プロセス用の代用モジュール examples/sample_f_mpi_stub.f90 (MPI_Init, MPI_Comm_rank, MPI_Comm_size, MPI_Finalize などを 1 プロセスとして実装したもの) で満たす. コマンドの例はクイックスタートの「C言語」と「Fortran」の「MPI なし」に示す.

　利用者のプログラムは MPI ありと同じ書き方で動く. 違いは次のとおりである.

  • C++: コミュニケータは parcel::comm comm(&q); で作る (MPI ありの parcel::comm comm(MPI_COMM_WORLD, &q); に当たる). mpi_rank() は 0, mpi_size() は 1 を返す. set_crsMat(&comm, nstart, nend, n, nnz, ...) はそのまま使えるが, 1 プロセスが全体を持つので nstart = 0, nend = n - 1 とする (違えば std::invalid_argument). MPI の型を使う関数 (comm::mpi_comm() など) は無い. 利用者のプログラム中の MPI の呼び出し (MPI_Init など) は #if PARCEL_MPI で分ける (examples/quick_start.cpp を参照).
  • C言語: ラッパ (capi/wrapper_parcel_sycl.cpp) と, parcel_sycl_c.h をインクルードするプログラムの両方を -DPARCEL_MPI=0 でコンパイルする (食い違うとコミュニケータの引数の型が合わない). 関数名と引数の並びは同じで, コミュニケータの引数の型 (PARCEL_C_COMM) は int になり, 値は使われない (0 を渡す). nstart = index_base, n_local = n_global とする (違えば PARCEL_ERR_DISTRIBUTION). ライブラリ内の例外は MPI_Abort せず, メッセージを表示して PARCEL_ERR_RUNTIME を返す. MPI_Init は要らない.
  • Python: 既定で MPI なしの版になる (インストールの「Python のパッケージ」). mpirun を使わずに python script.py で実行する.
  • Fortran: モジュール capi/parcel_sycl_mod.f90 はそのまま使う (コミュニケータの整数は使われない). examples/sample_f.f90 は変えずに, 1 プロセス用の mpi モジュールの代用 examples/sample_f_mpi_stub.f90 と一緒に gfortran でコンパイルする.


4.8 Python のパッケージ

　Python のパッケージ parcel (配布パッケージの python/) は, PARCEL の C++ のライブラリを直接呼ぶネイティブ層 (libparcel_py.so) をソースからビルドして入れる. 必要なものは, PARCEL をビルドできる環境 (SYCL 対応コンパイラの章の「使用時の設定」), Python 3.8 以上と NumPy である. 行列を作るには SciPy が便利であり, 回帰試験の Python の試験 (tests/regression/sample_py.py) も SciPy を使う. ネイティブ層は AdaptiveCpp でビルドする. 既定は MPI なしの 1 プロセス版であり, ビルドの設定 PARCEL_MPI=1 で MPI ありの版になる. 入れ方は次の 3 通りである. 使い方は使用方法の Python に示す.

  • spack のレシピ py-parcel-sycl で入れる (「spack によるインストール」). ゼロから入れるスクリプト spack/stack/install_stack.sh は C++ のヘッダ, C言語・Fortran の API と一緒にこのパッケージも入れる.
  • python/ で pip install . を実行する (下の「MPI なし (既定)」).
  • pip を使わずにネイティブ層を直接ビルドし, 環境変数でその場所を与える (同上).

4.8.1 環境ごとの設定

　ネイティブ層は環境 (SYCL のターゲットと MPI の有無) ごとにビルドする. ビルドの設定は pip の-C cmake.define.<名前>=<値>で与える (「ビルドの設定」). 本書の試験環境で用いた値を次に示す (推奨オプションと同じ). 空欄は既定値のままでよい.

環境 PARCEL_TARGET PARCEL_KERNEL_FLAGS PARCEL_EXTRA_FLAGS
s86 (CPU), Miyabi-C, PS-A (omp) (-D_BLOCKING_LOOP_DOT_=1)
s86 (V100) cuda:sm_70 (-DPARCEL_SPMV_LADDER=0 -DPARCEL_PRECON_LADDER=0. 梯子分割なし) -Xcuda-ptxas -maxrregcount=255
Aquarius (A100) cuda:sm_80 (同上)
Miyabi-G (GH200) cuda:sm_90 (同上)
PS-B (MI300A) hip:gfx942 (-DPARCEL_SPMV_LADDER=1 -DPARCEL_PRECON_LADDER=1)
macOS (Apple シリコン) + Homebrew omp.library-only (-D_BLOCKING_LOOP_DOT_=1)

　括弧の値は既定値 (PARCEL_KERNEL_FLAGS はターゲットから決まる値) である. LAPACKE の場所 (LAPACKE_INCLUDE_DIR, LAPACK_LIBS) は環境に合わせて与える (PS-A・PS-B では -l:libopenblaso.so.0 など. 推奨オプションの各環境の節). ビルド・インストール・実行のいずれも, 同じ環境 (SYCL 対応コンパイラの章の「使用時の設定」. AdaptiveCpp・LAPACK・MPI のライブラリが見つかる状態) で行う.

　macOS では, Homebrew で入れた環境 (「SYCL対応コンパイラのインストール方法」の「macOS (Homebrew)」) で python/envs/mac_brew.sh を読み込むと, 上の表の値と Homebrew の OpenBLAS の場所が環境変数に設定されるので, その後で下の pip または直接のビルドを行う.

4.8.2 MPI なし (既定)

　pip は python/ で実行する. pip はビルドに scikit-build-core と CMake 3.18 以上を使う (無ければ取得する) ので, パッケージの置き場に接続できる必要がある. venv の pip は先に更新しておく (古い pip はビルドの設定を渡す -C を受け付けないことがある). ログインノードで実行してよく, 1〜2 分かかる.

python3 -m venv $HOME/venv_parcel
$HOME/venv_parcel/bin/python -m pip install -U pip
$HOME/venv_parcel/bin/python -m pip install scipy           # 任意. 行列を作るのに便利 (parcel の依存は NumPy だけ)
cd python
$HOME/venv_parcel/bin/python -m pip install . -C cmake.define.PARCEL_TARGET=cuda:sm_70 \
    -C "cmake.define.PARCEL_EXTRA_FLAGS=-Xcuda-ptxas -maxrregcount=255"     # s86 (V100) の例

　ネイティブ層は acpp で直接ビルドし, MPI のライブラリをリンクしない.

　pip を使わない場合は, ネイティブ層を直接ビルドし, 環境変数 PARCEL_PY_LIB にその場所を, PYTHONPATH に python/ を与える (パッケージのトップディレクトリで実行する. 回帰試験の Python のジョブもこの形で, tests/regression/sub_build_lang_<環境>.sh が bin/<環境>/libparcel_py.so を作る).

acpp -O3 --acpp-targets=omp -DPARCEL_MPI=0 -march=native -mtune=native -D_BLOCKING_LOOP_DOT_=1 \
     -fPIC -shared -IInclude -I/usr/include/openblas -o libparcel_py.so python/src/parcel_py.cpp -lopenblas
PYTHONPATH=python PARCEL_PY_LIB=$PWD/libparcel_py.so python script.py

　入ったことは次のように確かめる. parcel.has_mpi() は MPI ありの版なら True を返す. parcel.build_info() はビルドの設定を, parcel.device_name() は使われるデバイスの名前を返す.

$HOME/venv_parcel/bin/python -c "import parcel; print(parcel.has_mpi(), parcel.build_info(), parcel.device_name())"

　Python の API の試験 tests/regression/sample_py.py は, C言語の examples/sample_c.c と同じ問題・項目・判定 (7 種のソルバ, QQ を作らない pcagmres の 2 通り, ks_arnoldi の shift-invert など) を Python から行う. 回帰試験の言語 python として流せるほか (「パッケージの構成」), 単独でも動く. 引数は NX である.

PARCEL_TEST_FROM_SOURCE=1 PARCEL_PY_LIB=$PWD/libparcel_py.so python tests/regression/sample_py.py 16   # パッケージの python/ を読む
python tests/regression/sample_py.py 16                                                                # インストールした parcel を読む

4.8.3 MPI あり

　ビルドの設定 PARCEL_MPI=1 を与えると, ネイティブ層を MPI の C++ ラッパ (既定 mpicxx) でビルドする. ラッパが中で acpp を呼ぶよう, OMPI_CXX=acpp (Open MPI) などを先に設定しておく. mpi4py は任意であり, 使う場合は同じ MPI でビルドしたものを venv に入れる.

export OMPI_CXX=acpp
python3 -m venv $HOME/venv_parcel_mpi                       # MPI なしの版とは別の venv にする
$HOME/venv_parcel_mpi/bin/python -m pip install -U pip
cd python
$HOME/venv_parcel_mpi/bin/python -m pip install . -C cmake.define.PARCEL_MPI=1

　pip を使わない場合は, 上のacppの行をmpicxxにし, -DPARCEL_MPI=0を外す. 実行は「MPI ありでの実行」に示す.

　試験の状況: pip で入れたパッケージとソースからビルドしたものの両方が, MPI ありの版で s86 (CPU, V100), Miyabi-C, Miyabi-G, PS-A, PS-B, Aquarius のすべての項目に合格した. MPI なしの版は s86, Aquarius, macOS (Homebrew. MPI ありの版も) で確認した. spack で入れた py-parcel-sycl の確認は「spack によるインストール」に示す.

　pip の -C cmake.define.<名前>=<値> で与える名前を次に示す (python/CMakeLists.txt の先頭に同じ一覧がある). 値を与えなければ右の列の既定値になる.

4.9 spack によるインストール

　配布パッケージの spack/ には, PARCEL を spack で入れるためのレシピと, spack の取得から LLVM・AdaptiveCpp・OpenBLAS・Python, PARCEL までをゼロから入れるスクリプトがある. 説明の原文は spack/README.ja.md (英語版は spack/README.md) である. spack は 1.x (パッケージリポジトリの API v2.2) を対象とする.

spack -e <環境> develop --no-clone --path <パッケージ> parcel-sycl@1.2.0
spack -e <環境> develop --no-clone --path <パッケージ> py-parcel-sycl@1.2.0
spack -e <環境> add "parcel-sycl@1.2.0 ~mpi ~cuda ~rocm" "py-parcel-sycl@1.2.0 ~mpi ~cuda ~rocm"                    # CPU
spack -e <環境> add "parcel-sycl@1.2.0 ~mpi +cuda cuda_arch=70" "py-parcel-sycl@1.2.0 ~mpi +cuda cuda_arch=70"     # GPU
spack -e <環境> concretize -f && spack -e <環境> install

　使うときは, 構成を指定して spack load する. spack load parcel-sycl は, 利用者のプログラムを PARCEL と同じ設定でコンパイルするための PARCEL_CXXFLAGS (ターゲット, 最適化, MPI の有無, ヘッダの場所) と PARCEL_LDFLAGS (実行時に要るライブラリ (LLVM の libomp, AdaptiveCpp, LAPACK, MPI) の RPATH と LAPACK) を設定する. MPI ありの版では OMPI_CXX=acpp なども設定するので, mpicxx で同じようにコンパイルする. MPI のラッパ経由では libomp の RPATH が付かないので, PARCEL_LDFLAGS を必ず付ける. C言語・Fortran の API のヘッダ (parcel_sycl_c.h, parcel_sycl_mod.mod) とライブラリの場所は spack load では設定されないので, spack location -i で調べて -I, -L, -Wl,-rpath に与える.

spack env activate <環境>
spack load parcel-sycl+cuda py-parcel-sycl+cuda                   # 構成を指定して読む
acpp $PARCEL_CXXFLAGS -O3 -o prog prog.cpp $PARCEL_LDFLAGS        # C++
P=$(spack location -i parcel-sycl+cuda)                           # C言語 (MPI なしの版): 場所は自分で与える
gcc -I$P/include -o prog prog.c -L$P/lib -lparcel_sycl_c -Wl,-rpath,$P/lib
python script.py                                                  # Python

　注意点を次に示す.

  • ルートの仕様は ~cuda ~rocm まで明示する. parcel-sycl ~mpi だけでは, 解決の統合 (unify) で GPU 版と同じものにまとめられることがある.
  • CPU 版と GPU 版を同じ環境に入れるとビューで重なるので, 環境のビューから parcel-sycl・py-parcel-sycl を除外する (view: default: {root: .spack-env/view, exclude: [parcel-sycl, py-parcel-sycl]}).
  • 解決済みの環境に仕様を足すと, concretize が内部エラー (unsatisfiable) になることがある. concretize -f で解決し直す.
  • MPI と hipsycl (AdaptiveCpp) は環境の中で 1 つにそろえる (packages:mpi:require: に版と構成まで, packages:hipsycl:require:). 外部登録の MPI が複数あると, 別の構成 (CUDA 版など) が選ばれることがある.
  • AdaptiveCpp が使う CUDA は, ビルド時の ACPP_CUDA_PATH (または spack の cuda) を記録し, spack load で同じ値を設定する. ドライバより新しい CUDA を使わないよう, 外部パッケージの cuda かこの変数で指定する.
  • LAPACKE のヘッダは include/lapacke/ に写す (計算ノードに lapacke.h が無い環境のため).
  • spack develop のソースの中で試験を実行すると (bin/, __pycache__ などができる), spack は更新ありとみなし, 次の install で PARCEL を作り直す. 試験はソースの写しで行う.

4.9.2 配布 tarball から入れる

　レシピは配布 tarball の url と sha256 を持つ. url は GitHub の Release に置く tarball (https://github.com/parcel-jaea/PARCEL-release/releases/download/v1.2.0/parcel_sycl-1.2.0.tar.gz) を指し, sha256 は tools/make_tarball.py --pin がレシピに書く (「配布物の確認」). spack develop を使わなければ, spack は url から tarball を取得する (parcel-sycl と py-parcel-sycl は同じ tarball を使う). 計算機が外部に接続できないときは, tarball を spack の mirror の形 (<mirror>/_source-cache/archive/<sha256 の先頭 2 文字>/<sha256>.tar.gz) に置き, spack mirror add で登録する. spack は取得した tarball をレシピの sha256 と照合し, 違えば止まる. sha256 は spack のハッシュに入るので, 書き直すと (spack develop で使う場合も) PARCEL が作り直される. 手順は spack/README.ja.md の「配布 tarball から入れる」に示す.

4.9.3 構成の選び方

　入れる構成は, パッケージ (parcel-sycl, py-parcel-sycl) とバリアントの組合せ (仕様) で選ぶ. 目的ごとの仕様の例を示す (版の@1.2.0は省略した).

目的 仕様
CPU, MPI なし (C++・C言語・Fortran) parcel-sycl ~mpi ~cuda ~rocm
CPU, MPI あり parcel-sycl +mpi ~cuda ~rocm
NVIDIA の GPU (A100 の例) parcel-sycl ~mpi +cuda cuda_arch=80
NVIDIA の GPU, MPI あり parcel-sycl +mpi +cuda cuda_arch=80
AMD の GPU (MI300A) parcel-sycl ~mpi +rocm amdgpu_target=gfx942
C++ (ヘッダ) だけ. C言語・Fortran の API を作らない parcel-sycl ~capi ~mpi ~cuda ~rocm
Python も使う 同じ構成のpy-parcel-syclも並べる (例: py-parcel-sycl ~mpi ~cuda ~rocm)
  • 言語の選び方: C++ (ヘッダ) はparcel-syclに常に入る. C言語と Fortran の API はバリアントcapi (既定 on) でまとめて入れるか外すかを選び, どちらか一方だけは選べない. Python は別のパッケージpy-parcel-syclを加えるかどうかで選ぶ.
  • +capi (既定) では Fortran のコンパイラが必要である (Fortran のモジュールを作るため). Fortran のコンパイラが無い環境では~capiにする.
  • py-parcel-syclはビルドにparcel-syclを使うので, Python だけを入れる場合もparcel-syclが入る. このときparcel-syclは既定の+capiになる. Fortran のコンパイラが無い環境ではpy-parcel-sycl ~mpi ~cuda ~rocm ^parcel-sycl ~capiのようにparcel-syclのバリアントを添える (s86 で解決できることと, parcel-syclが Fortran のコンパイラを使わなくなることを確かめた). ただし LAPACK に使う OpenBLAS も既定では Fortran のコンパイラを使うので, Fortran のコンパイラがまったく無い環境ではopenblas ~fortranも指定する (Odyssey の定義wis_odyと同じ).
  • +cudaと+rocmは同時に指定できない (レシピがエラーにする). どちらも付けなければ CPU (OpenMP) 版である. GPU ではcuda_arch (CUDA の計算能力. V100 70, A100 80, GH200 90) またはamdgpu_targetを 1 つ指定する.
  • +mpiには MPI が要る. 計算機の MPI を外部パッケージとして環境の定義に登録しておく (MPI とhipsyclは環境の中で 1 つにそろえる. 上の注意).
  • py-parcel-syclのmpi・cuda・rocmなどは, 組み合わせるparcel-syclと同じにする (レシピが同じ構成のparcel-syclを求める).

　ゼロから入れる方法では, 入れる構成はspack/stack/envs/<環境>/spack.yamlのspecs:に並べたものである. 同梱の定義は, その環境で使える構成をすべて並べている (例えば s86 は CPU / GPU × MPI なし / あり × parcel-sycl / py-parcel-sycl の 8 行). 構成を絞る・変えるときは, install_stack.shを実行する前にspecs:を書き換える. 例えば CPU・MPI ありの C++・C言語・Fortran と Python だけを入れる場合は次のようにする. 入れた後に書き換えた場合も, 同じコマンドでinstall_stack.shを流し直せば, 解決し直して足りないものだけを入れる.

spack:
  specs:
  - parcel-sycl@1.2.0 +mpi ~cuda ~rocm         # CPU・MPI あり (C++・C言語・Fortran)
  - py-parcel-sycl@1.2.0 +mpi ~cuda ~rocm      # 同じ構成の Python

4.9.4 ゼロから入れる

　既存の spack を使わず, spack の取得から PARCEL までを spack/stack/install_stack.sh の 1 本で入れる. 引数は環境の名前 (spack/stack/envs/ の下のディレクトリ名), 入れ先, 並列数である.

bash spack/stack/install_stack.sh s86 $HOME/parcel_stack 16           # <環境> <入れ先> [並列数]
bash spack/stack/check_stack.sh $HOME/parcel_stack $HOME/parcel_check  # ログインノードでの確認
. $HOME/parcel_stack/setup.sh                                          # 使うとき
spack load parcel-sycl+mpi+cuda py-parcel-sycl+mpi+cuda
  • spack で作るもの: LLVM 18.1.8, AdaptiveCpp (hipsycl 24.10.0), OpenBLAS, binutils, Python 3.11 と NumPy・SciPy・pip, PARCEL 本体・C言語と Fortran の API・Python のパッケージ.
  • 各環境の既存品を使うもの: コンパイラ, CUDA / ROCm, MPI. 計算機のネットワークやドライバと結び付くため, spack/stack/envs/<環境>/spack.yaml に外部パッケージとして書く.
  • spack 本体 (1.1.0.dev0) とレシピ集 (spack-packages) は, 確認した版に固定する (install_stack.sh の先頭).
  • 入れ先の中に spack・設定・キャッシュをすべて置き, ~/.spack と /etc/spack を読まない (SPACK_DISABLE_LOCAL_CONFIG=1). 既存の spack の環境に影響されず, 影響も与えない.
  • PARCEL のソースは install_stack.sh の 2 つ上のディレクトリ (配布パッケージのトップ. Include/, capi/, python/ があること) である. 別の場所を使うときは PARCEL_SRC=<ディレクトリ> を与える.
  • envs/<環境>/site_env.sh はインストール中と setup.sh を読んだときに読む (サイトの MPI などのモジュール). after_activate.sh は環境を有効にした後に読む. compilers.yaml は本体より先に入れるコンパイラ (OS の GCC が古い環境で新しい GCC を作る) である.
  • 途中で止まったら, 同じコマンドで再開できる (入ったものは使い回す). CONCRETIZE_ONLY=1 を付けると解決だけを行う.
  • check_stack.sh は入っている構成ごとに spack load し, Python から parcel を読めるか, examples/ の sample_c.c・sample_f.f90・quick_start.cpp がビルドでき, 実行に要るライブラリがすべて見つかるかを調べる (実行はしない). MPI なしの Fortran は examples/sample_f_mpi_stub.f90 と一緒にコンパイルする.
  • インストール後の試験は spack test run parcel-sycl py-parcel-sycl (結果は spack test results). インストール先のヘッダとライブラリでクイックスタートの例 (parcel-sycl は C++ と, +capi なら C言語・Fortran. py-parcel-sycl は quick_start.py) をビルドして実行し, 厳密解との最大相対誤差が 1e-6 以下かを判定する (「ビルド後の確認」 と同じ). MPI ありの版は MPIEXEC (既定は MPI の bin/mpiexec)・MPIEXEC_NP_FLAG・MPI_NP (既定 2)・MPIEXEC_ARGS で起動する. GPU の版は, GPU の無いノード (ログインノード) ではビルドだけを試験して実行は SKIPPED になるので, GPU の計算ノードでも実行する. PARCEL_TEST_RUN=0 で実行を止められる. スレッド数と実行場所の判定は「ビルド後の確認」と同じ (OMP_NUM_THREADS が無ければ計算ノードは使える論理 CPU 数のすべて, ログインノードは 4. QUICK_NODE で強制) で, 判定と使った値は spack test results -l の出力に出る. +fj +mpi (富士通の mpiexec) は RC_ONLY=1 が既定である (外すときは RC_ONLY=0). Intel MPI では C言語・Fortran の試験を同じ場所の汎用のラッパ (mpicc, mpif90) で組み, 中身のコンパイラを I_MPI_CC, I_MPI_F90 (と I_MPI_FC) で spack のコンパイラ (gfortran など) にする (spack が返す mpiifx は ifx を呼び, gfortran で作った parcel_sycl_mod.mod を読めない). GPU の版の実行と +fj は計算ノード (短いバッチジョブか対話ジョブ) で流す. CPU の版はログインノードでもよい (施設の規則に従う).

4.9.6 試験環境以外の計算機

　上の 7 環境以外の Linux の計算機では, 雛形 spack/stack/envs/generic/ を写して書き換え, install_stack.sh で入れる. 雛形は s86 と Miyabi-C の定義にならって作ったものである. Ubuntu 24.04 (WSL2. OS の GCC 13.3.0, Open MPI 4.1.6, NVIDIA のリポジトリの CUDA 12.6, RTX A6000) で, 下の手順のとおりに書き換えて CPU・GPU (cuda_arch=86) × MPI なし・ありの 8 構成を入れ, check_stack.sh, クイックスタート (C++・C言語・Python), 検証用サンプル (pcg・pgmres・ks_arnoldi) が合格した. Rocky Linux 9.8 (RHEL 9 互換. WSL2. OS の GCC 11.5.0, Open MPI 4.1.1, NVIDIA のリポジトリの CUDA 12.6) でも同じ 8 構成を入れ, 同じ試験が合格した. RHEL 系の OS の Open MPI は, ヘッダを含めて 1 つのディレクトリに並べてから登録する (「MPI と CUDA を登録する」).

cp -r spack/stack/envs/generic spack/stack/envs/mysite           # 写して書き換える
CONCRETIZE_ONLY=1 bash spack/stack/install_stack.sh mysite $HOME/parcel_stack   # 解決だけを試す
bash spack/stack/install_stack.sh mysite $HOME/parcel_stack 16                  # 入れる

　書き換える箇所はspack.yamlの先頭のコメントに手順として書いてある.

  • コンパイラ (GCC) の版と場所 (gcc --version, which gcc g++ gfortranで調べる).
  • MPI を使う場合は, specs:の+mpiの 2 行とpackages:のmpi・openmpiの行のコメントを外し, 版と場所を書き換える (書き方は「一般的な Linux」).
  • NVIDIA の GPU を使う場合は, +cudaの行とcudaの行のコメントを外し, cuda_arch (「GPU で動かす」で調べる), CUDA の版と場所を書き換え, hipsyclとllvmの行を GPU 用に替える. AMD の GPU は PS-B の定義psb (ROCm の外部登録) を下敷きにする.
  • CPU が x86_64 でなければ, llvmのtargetsを書き換える (Arm はaarch64).
  • モジュールで MPI などを読む計算機では, site_env.shにmodule loadを書く (RHEL 系の OS の Open MPI はmodule load mpi/openmpi-x86_64. 雛形のsite_env.shに例がある). メモリが少ない計算機ではPARCEL_STACK_JOBSで同時コンパイル数を下げる.

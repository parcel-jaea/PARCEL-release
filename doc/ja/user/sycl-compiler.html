3 SYCL対応コンパイラのインストール方法

　SYCL版PARCELはヘッダーファイルのみで構成されており, 利用にはSYCL対応コンパイラが必要である. v1.2 の試験では, すべての環境で AdaptiveCpp (旧名 hipSYCL / Open SYCL) を用いた. AdaptiveCpp は LLVM (clang) をフロントエンドとし, 1 つのソースから CPU (OpenMP) ・NVIDIA GPU (CUDA) ・AMD GPU (HIP) 向けのコードを生成できる.

  • AdaptiveCpp: https://github.com/AdaptiveCpp/AdaptiveCpp
  • インストール手順 (公式): https://github.com/AdaptiveCpp/AdaptiveCpp/blob/develop/doc/installing.md
  • spack: https://spack.readthedocs.io/

　ソースコードからビルドすることもできるが, 本版の試験環境ではいずれも spack で導入した. spack 上のパッケージ名は hipsycl である. spack 環境 (spack env) を使うかどうかと環境名, spack のインストール先は利用者が決める. 以下の例ではこれらを<spack 環境名>・<spack のインストール先>と書く (試験で用いた名前は各環境の表に示す). spack 環境を使わない場合はspack env activateの行を省き, spack installの--addを外す. コンパイラドライバは acpp で, 生成するコードの種類は --acpp-targets= で指定する.

　本章の手順は既存の spack に AdaptiveCpp を入れる方法である. このほか, 配布パッケージの spack/stack/install_stack.sh を使えば, spack の取得から LLVM・AdaptiveCpp・OpenBLAS・Python, PARCEL 本体と C言語・Fortran・Python の API までを, 既存の spack と切り離した新しい spack 環境にまとめて入れられる (MPI・CUDA / ROCm・コンパイラは各環境の既存品を使う. インストールの章の「spack によるインストール」). macOS では spack を使わず, Homebrew で AdaptiveCpp を入れる (「macOS (Homebrew)」). 試験環境以外の Linux の計算機での手順は「一般的な Linux」に, LAPACKE の入れ方は「LAPACKE の入れ方」に示す.

　試験時の環境の構成例を, 次節以降の環境ごとの節の冒頭の表に示す (環境と装置の名前は用語集を参照. 装置欄は計算ノードの構成である). モジュールの版などはサイトの更新で変わりうる. 8 環境の AdaptiveCpp はいずれも同じコミット 7677cf6e (24.10.0+git.7677cf6e.20241220) である.

　ログインノードと計算ノードでCPUアーキテクチャが異なる場合 (Odyssey など) には, AdaptiveCpp も PARCEL も計算ノード上でビルドする. 両者のアーキテクチャが一致する環境ではログインノードでビルドしてよい. ただし -march=native を付ける場合は, ログインノードと計算ノードの CPU 世代が一致していることを確認する.

　--acpp-targets=omp で OpenMP バックエンドを使う場合, リンクされる libomp の版によって実行時のスレッド固定の挙動が異なる. LLVM 18.1.8 の libomp (s86 CPU, PS-A) では OMP_PROC_BIND を設定すると全ワーカースレッドが 1 コアに集約され, 大幅に遅くなる. 対処として, 実行時にOMP_PROC_BINDを設定しないかfalseにする (spreadなど他の値でも同じ症状になる). ランクごとのコアの割り当てはmpirunのバインド (--bind-to coreなど) で行えば, スレッドはその範囲に収まる.

　s86 の CPU ノードは Intel Xeon Gold 6242R (20 コア ×2), GPU ノードは Intel Xeon Gold 6248R (24 コア ×2) + NVIDIA V100-SXM2-32GB ×4 である. spack で LLVM 18 と AdaptiveCpp を導入する. CPU 用と GPU 用を別々に導入する必要はなく, CUDA バックエンド付き (+cuda) の AdaptiveCpp 1 つを spack 環境 (試験では sycl) に置き, --acpp-targets=omp と --acpp-targets=cuda:sm_70 の両方に使う.

インストール (最初に 1 回. CPU・GPU 共通)

module purge
module load gnu/9.5.0
module load openmpi/cur
. <spack のインストール先>/share/spack/setup-env.sh
spack env create <spack 環境名>      # 初回のみ
spack env activate <spack 環境名>
spack compiler find
spack external find
spack install --add llvm@18
spack install --add hipsycl +cuda % llvm@18

　この hipsycl の既定の CUDA パスは spack の cuda@12.9.0 を指しているが, V100 用のビルドではサイトの CUDA 12.6 を ACPP_CUDA_PATH で指定して上書きする.

使用時の設定 (CPU)

module purge
module load gnu/9.5.0
module load openmpi/cur
. <spack のインストール先>/share/spack/setup-env.sh
spack env activate <spack 環境名>
spack load hipsycl
export sycl_root=`spack location -i hipsycl`
export llvm_root=`spack location -i llvm`
export LD_LIBRARY_PATH=$sycl_root/lib/:$llvm_root/lib/:${LD_LIBRARY_PATH}
export KMP_STACKSIZE=1G
export MPICXX_CXX=acpp
export OMPI_CXX=acpp

使用時の設定 (GPU)

module purge
module load gnu/9.5.0
module load openmpi/cur
module load cuda/12.6
. <spack のインストール先>/share/spack/setup-env.sh
spack env activate <spack 環境名>
spack load hipsycl
export sycl_root=`spack location -i hipsycl`
export llvm_root=`spack location -i llvm`
export cuda_root=/home/app/cuda/12.6
export ACPP_CUDA_PATH=$cuda_root
export LD_LIBRARY_PATH=$sycl_root/lib/:$llvm_root/lib/:$cuda_root/lib64:${LD_LIBRARY_PATH}
export KMP_STACKSIZE=1G
export MPICXX_CXX=acpp
export OMPI_CXX=acpp

3.2 Odyssey (Wisteria-Odyssey, A64FX)

項目 値
装置 (CPU / GPU) A64FX (48 コア)
OS RHEL 8 (計算ノード)
ホストコンパイラ 富士通 FCC tcsds-1.2.43 (fj/1.2.43, clang モード)
MPI 富士通 MPI 1.2.43 (fjmpi/1.2.43)
CUDA / ROCm —
AdaptiveCpp 24.10.0 (~cuda)
LLVM (clang) 18.1.8 (spack, GCC 8.3.1 でビルド)
導入方法 (spack 環境) spack, odyssey (計算ノードでビルド)
BLAS / LAPACK 富士通 LAPACK (-lfjlapack)
--acpp-targets omp.library-only

　Odyssey の計算ノードは A64FX (48 コア, 4 CMG) で, ログインノードとアーキテクチャが異なる. このため AdaptiveCpp のインストールも PARCEL のビルドも計算ノード上で行う (バッチジョブまたは対話ジョブで spack を実行する).

　Odyssey では --acpp-targets=omp.library-only を用いる. このモードでは AdaptiveCpp は SYCL のランタイムライブラリとしてのみ働き, カーネルを含むコード全体をホスト側の C++ コンパイラがコンパイルする. ホストコンパイラには富士通コンパイラ (FCC, clang モード) を ACPP_CPU_CXX で指定する. これにより富士通コンパイラの A64FX 向けの最適化と富士通の OpenMP ランタイムが使われる. ただし AdaptiveCpp はACPP_OMP_CXX_FLAGSの後ろに-O3を付けるので, -Kfastは効かない. 積和の FMA へのまとめは推奨オプションのとおりコマンドラインの-ffp-contract=fastで指定する. LLVM は 18.1.8 を spack で導入し, spack 環境 (試験では odyssey) に置いた. MPI は富士通 MPI (mpiFCC), LAPACK は富士通 LAPACK (-lfjlapack) を用いる.

インストール (最初に 1 回. 計算ノードで行う)

　A64FX 向けの LLVM と AdaptiveCpp は計算ノードでビルドする. 試験で用いた spack 環境の定義はllvm@18とhipsycl %clang@18の 2 つであり, OS 付属の GCC 8.3.1 で LLVM 18.1.8 をビルドし, その clang で AdaptiveCpp 24.10.0 (CUDA なし. ~cudaは既定) をビルドした. 次のバッチジョブで同じものを作れる (spack は 1.1.0.dev0 を用いた).

　計算ノードでのビルドでは, 並列数, メモリの上限, 処理時間に注意する.

  • 並列数: spack installの-jで同時に動かすコンパイルの数を決める. 既定 (論理 CPU 数. A64FX では 48) や-j32では LLVM のビルドでメモリが足りなくなる. 試験では-j12とした.
  • メモリの上限: A64FX の 1 ノードのメモリは HBM2 の 32 GiB で, 利用者のジョブが使えるのはそのうち約 28 GiB である. LLVM のコンパイルとリンクは 1 本あたりのメモリが大きい. -j32ではピークが約 29 GiB に達し, メモリ不足でジョブが止まった. 止まった場合は-jを下げて同じコマンドを流し直せば, 入ったものは使い回される.
  • 処理時間: A64FX の 1 コアは x86 の 1 コアより遅く, LLVM 18.1.8 のビルドに-j12で約 3 時間 (ビルド 1 時間 30 分, インストール 1 時間 25 分) かかった. LLVM を含む依存パッケージの全体には約 4 時間 30 分かかった. 経過時間の上限 (elapse) を十分に取り, 長時間の資源グループを使う. 試験ではelapse=24:00:00とした. 上限で止まった場合も, 同じジョブを流し直せば続きから入る.
#!/bin/bash
#PJM -L "rscgrp=<リソースグループ>"
#PJM -L "node=1"
#PJM -L "elapse=24:00:00"           # LLVM のビルドに約 3 時間 (-j12). 長時間の資源グループを使う
#PJM -g <グループ>
#PJM -j

. /etc/profile.d/modules.sh
module purge
module load odyssey
JOBS=12                               # 同時コンパイル数. 32 以上では LLVM のビルドでメモリ (約 28 GiB) が足りない
export SPACK_ROOT=<spack のインストール先>
# (任意) spack の利用者設定とキャッシュをホーム以外に置く場合
export SPACK_USER_CONFIG_PATH=<spack の利用者設定の置き場所>
export SPACK_USER_CACHE_PATH=<spack のキャッシュの置き場所>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env create <spack 環境名>      # 初回のみ
spack env activate <spack 環境名>
spack compiler find                  # OS の GCC 8.3.1 などを登録する
spack install -j ${JOBS} --add llvm@18
spack install -j ${JOBS} --add hipsycl %clang@18

使用時の設定

　Odyssey では, 次の設定もビルドと同じく計算ノード (ジョブの中) で行う.

. /etc/profile.d/modules.sh
module purge
module load odyssey
export SPACK_ROOT=<spack のインストール先>
# (任意) spack の利用者設定とキャッシュをホーム以外に置く場合
export SPACK_USER_CONFIG_PATH=<spack の利用者設定の置き場所>
export SPACK_USER_CACHE_PATH=<spack のキャッシュの置き場所>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env activate <spack 環境名>
export sycl_root=`spack location -i hipsycl`
export llvm_root=`spack location -i llvm@18`
export fj_root=/opt/FJSVxtclanga/tcsds-1.2.43
export LD_LIBRARY_PATH=$sycl_root/lib/:$llvm_root/lib/:$fj_root/lib64/:${LD_LIBRARY_PATH}
export MPICXX_CXX=acpp
export OMPI_CXX=acpp
export ACPP_CPU_CXX="$fj_root/bin/FCC"
export ACPP_OMP_CXX_FLAGS="-O3 -Kopenmp -Kfast -std=c++17 -Nclang"

3.3 Aquarius (Wisteria-Aquarius, A100)

項目 値
装置 (CPU / GPU) Xeon Platinum 8360Y ×2 + A100-SXM4-40GB ×8
OS RHEL 8.10 (ログインノード)
ホストコンパイラ GCC 8.3.1 (gcc/8.3.1)
MPI Open MPI 4.1.1 (ompi/4.1.1, CUDA 非対応版)
CUDA / ROCm CUDA 12.2 (cuda/12.2)
AdaptiveCpp 24.10.0 (+cuda)
LLVM (clang) 18.1.8 (spack). 13.0.1 も併存
導入方法 (spack 環境) spack, aquarius
BLAS / LAPACK OpenBLAS 0.3.15 (OS)
--acpp-targets cuda:sm_80

　spack 環境に llvm@13.0.1 と llvm@18.1.8 が併存するので, spack location -i llvm@18 のように版を明示する. CUDA 対応の Open MPI は別に ompi-cuda/4.1.5-12.2 がある.

　Aquarius の計算ノードは Intel Xeon Platinum 8360Y (36 コア ×2) + NVIDIA A100-SXM4-40GB ×8 である. spack 環境 (試験では aquarius) に AdaptiveCpp (CUDA バックエンド付き) と LLVM 18.1.8 を導入し, CUDA は 12.2 を用いた. ホストコンパイラは OS 付属の GCC 8.3.1 である. OpenMPI はサイトの ompi モジュール (試験時の既定は CUDA 非対応版の 4.1.1) を使い, spack 側の hwloc を LD_LIBRARY_PATH に加える.

インストール (最初に 1 回)

　試験で用いた spack 環境の定義はllvm@18 %gccとhipsycl+cuda %clang@18の 2 つであり, OS 付属の GCC 8.3.1 で LLVM 18.1.8 をビルドし, その clang で CUDA バックエンド付きの AdaptiveCpp 24.10.0 をビルドした. CUDA はcudaモジュールのサイトの CUDA 12.2 を spack の外部パッケージとして使い, OS の cmake・perl・python などのツールも外部パッケージとして登録した. 次の手順で同じものを作れる (spack は 1.1.0.dev0 を用いた).

. /etc/profile.d/modules.sh
module purge
module load aquarius
module load cuda
export SPACK_ROOT=<spack のインストール先>
# (任意) spack の利用者設定とキャッシュをホーム以外に置く場合
export SPACK_USER_CONFIG_PATH=<spack の利用者設定の置き場所>
export SPACK_USER_CACHE_PATH=<spack のキャッシュの置き場所>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env create <spack 環境名>      # 初回のみ
spack env activate <spack 環境名>
spack compiler find                  # OS の GCC 8.3.1 などを登録する
spack external find                  # OS のツール群と cuda モジュールの CUDA 12.2 を外部パッケージとして登録する
spack install --add llvm@18 %gcc
spack install --add hipsycl+cuda %clang@18

使用時の設定

. /etc/profile.d/modules.sh
module purge

export MPICXX_CXX=acpp
export OMPI_CXX=acpp

　LD_LIBRARY_PATHの先頭に spack の hwloc ($hwloc_root/lib) を置くのは, ライブラリの版の食い違いを避けるためである. サイトの Open MPI 4.1.1 は古い hwloc を使うので, それが先に読み込まれると, 新しい hwloc に合わせてビルドされた LLVM の OpenMP ランタイム (libomp.so) が読み込みに失敗し, AdaptiveCpp の CPU のバックエンドが使えなくなる (GPU 向けのビルドでも MPI ありの実行が止まる). spack の hwloc を先に探させると, 両者とも新しい hwloc を使う. spack のレシピ parcel-sycl も, spack loadのときに同じ設定を行う (インストールの「spack によるインストール」).

　Aquarius の OpenMPI 4.1 では, 同時に始まったジョブの mpirun が /tmp のセッションディレクトリを奪い合って起動に失敗することがある. 実行ジョブでは, mpirun の前にセッションディレクトリをジョブごとに分ける.

PARCEL_SESS=/tmp/parcel_${PJM_JOBID:-$$}
mkdir -p ${PARCEL_SESS}
export OMPI_MCA_orte_tmpdir_base=${PARCEL_SESS}
export OMPI_MCA_btl_vader_backing_directory=${PARCEL_SESS}
trap 'rm -rf ${PARCEL_SESS}' EXIT

spack compiler find                  # PATH にある GCC などを登録する
spack external find                  # cmake, perl, python などの OS のツールを外部パッケージとして登録する

　spack external find で登録した OS のツールは spack がビルドせずに使うので, インストールの時間が短くなる.

3.9.3 MPI と CUDA を登録する

　MPI と CUDA は計算機に入っているものを使い, spack では作らない. spack external find openmpi cuda で見つかることもあるが, モジュールで入れている計算機では見つからないことがあるので, spack 環境の定義 (spack.yaml. spack config edit で開く) に直接書く. 版と場所は自分の計算機に合わせる.

spack:
  packages:
    mpi:
      require: [openmpi]
    openmpi:
      buildable: false
      externals:
      - spec: openmpi@4.1.6~cuda
        prefix: /path/to/openmpi/4.1.6     # bin/mpicc がある場所の 1 つ上
    cuda:
      buildable: false
      externals:
      - spec: cuda@12.6.20
        prefix: /path/to/cuda/12.6
  • buildable: false は, spack がそのパッケージを自分で作らず, 登録したものだけを使う指定である.
  • MPI は環境の中で 1 つにそろえる. 外部登録の MPI が複数あると, 意図しない構成 (CUDA 版など) が選ばれることがある.
  • CUDA は, 計算ノードのドライバが対応する版以下を登録する (「GPU で動かす」).
  • OS のパッケージで入れた場合の例 (Ubuntu 24.04): Open MPI 4.1.6 はprefix: /usr, NVIDIA のリポジトリの CUDA 12.6 はspec: cuda@12.6.85とprefix: /usr/local/cuda-12.6. 版はmpirun --version, nvcc --versionで調べる.
  • OS のパッケージで入れた場合の例 (Rocky Linux 9): Open MPI 4.1.1 (openmpi-devel) はspec: openmpi@4.1.1~cuda, CUDA は Ubuntu と同じ. RHEL 系の OS の Open MPI は, bin/とlib/が/usr/lib64/openmpiに, ヘッダが/usr/include/openmpi-x86_64にある. spack はprefixの下のinclude/でヘッダを探すので, prefix: /usr/lib64/openmpiと書くと MPI に依存するパッケージ (MPI ありの PARCEL) のインストールがQuery of package 'openmpi' for 'headers' failedで止まる. 次のように 1 つのディレクトリに並べ, それをprefixに書く.
O=$HOME/openmpi-rhel                              # 置き場所は任意. OS のファイルは変えない
mkdir -p $O
ln -s /usr/lib64/openmpi/bin $O/bin
ln -s /usr/lib64/openmpi/lib $O/lib
ln -s /usr/lib64/openmpi/share $O/share
ln -s /usr/include/openmpi-x86_64 $O/include

3.9.4 LLVM と AdaptiveCpp のインストール

　OS の GCC で LLVM 18 をビルドし, その clang で AdaptiveCpp (spack のパッケージ名 hipsycl) をビルドする. GPU を使う場合は バックエンドをバリアントで指定する.

spack install --add llvm@18 %gcc
spack install --add hipsycl %clang@18                              # CPU だけ
# spack install --add hipsycl+cuda %clang@18                       # NVIDIA の GPU も使う場合 (上の代わり)
# spack install --add hipsycl+rocm amdgpu_target=gfx942 %clang@18  # AMD の GPU (MI300A の例) も使う場合

　LLVM のビルドは長い時間と多くのメモリを使う. 同時に動かすコンパイルの数はspack install -j <数>で決める. メモリが足りずに止まった場合は数を下げて同じコマンドを流し直す (入ったものは使い回す. Odyssey での例は「Odyssey」の節).

3.9.5 使用時の設定

export SPACK_ROOT=<spack のインストール先>
. $SPACK_ROOT/share/spack/setup-env.sh
spack env activate <spack 環境名>
export sycl_root=`spack location -i hipsycl`
export llvm_root=`spack location -i llvm@18`
export LD_LIBRARY_PATH=$sycl_root/lib:$llvm_root/lib:${LD_LIBRARY_PATH}
export ACPP_CUDA_PATH=<CUDA の場所>       # NVIDIA の GPU を使う場合
export OMPI_CXX=acpp MPICXX_CXX=acpp        # MPI のラッパ (Open MPI) に acpp を呼ばせる
  • LD_LIBRARY_PATHに LLVM のlib/を加えるのは, CPU 向けの実行ファイルが LLVM の OpenMP ランタイム (libomp.so) を使うためである. 代わりにリンク時に-Wl,-rpath,$llvm_root/libを付けてもよい (RPATH).
  • RHEL 系の OS の Open MPI は環境モジュールで読む (module load mpi/openmpi-x86_64. 読むまではmpicxx・mpirunがPATHに無い).
  • MPI のコンパイララッパにacppを呼ばせる変数は MPI によって異なる. Open MPI はOMPI_CXX, MPICH 系はMPICH_CXX, Intel MPI はI_MPI_CXXである (PS-A の例は「PS-A」の節).
  • LAPACKE の場所を調べ, コンパイルのフラグに与える (「LAPACKE の入れ方」).

　入ったことは, クイックスタートの C++ のプログラムをビルドして実行して確かめる. GPU では, 使われたデバイスの名前も確かめる (「GPU で動かす」).

3.9.6 Windows の WSL2

　Windows の WSL2 の Linux (Ubuntu, Rocky Linux) でも, この節の手順とinstall_stack.shで, CPU と NVIDIA の GPU を使える (Ubuntu 24.04 と Rocky Linux 9 で, RTX A6000 2 台を使って確かめた). Linux の計算機と違う点を示す.

  • 仮想ディスクの大きさ: OS, CUDA, install_stack.shの入れ先で 20〜30 GB を使った. wsl --installは既定でシステムドライブに置くので, 空きが少なければwsl --install --location <場所>か, 配布元の WSL 用のイメージ (Ubuntu のルートファイルシステム, Rocky Linux のRocky-9-WSL-Base-<版>.x86_64.wslなど) を取得してwsl --import <名前> <場所> <ファイル>で別のドライブに置く.
  • メモリと CPU: WSL2 が使う上限は Windows 側の%UserProfile%\.wslconfig ([wsl2]のmemory=, processors=) で決まる. LLVM のビルドの並列数はこのmemoryに合わせる (memory=24GBで-j 16で入った).
  • GPU: ドライバは Windows 側に入れ, WSL2 の中には入れない. CUDA は NVIDIA の WSL 用のaptリポジトリ (wsl-ubuntu) からツールキットだけを入れる (apt install cuda-toolkit-12-6. 入れ先は/usr/local/cuda-12.6). RHEL 系 (Rocky Linux 9) には WSL 用のリポジトリが無いので, 通常のrhel9のリポジトリのcuda-toolkit-12-6を入れる (ドライバのパッケージは入らず, libcuda.soは WSL のものが使われる. 入れ先は同じ). nvidia-smiとドライバのライブラリは/usr/lib/wsl/libにある. 通常のシェルではPATHに入っているが, systemd のサービスなどでは入っていない.
  • 複数の GPU: gpu_bind.sh (「1 ランクと 1 デバイスの対応」) で各ランクに別の GPU を割り当てられる. 挟まないと全ランクが同じ GPU を使う.
  • 長いビルド: WSL2 は, そのディストリビューションを使うシェルがすべて終わるとしばらくして止まり, 中で動いているビルドも止まる. 端末を開いたまま流すか, Windows 側でwsl -d <名前> -- sleep infinityのようなプロセスを残しておく.

3.10 LAPACKE の入れ方

　PARCEL の固有値ソルバ ks_arnoldi は LAPACKE (LAPACK の C 言語の呼び出し口) を使う. 既定では全ソルバがビルドに入るので, 線形ソルバだけを使う場合もヘッダ lapacke.h とライブラリが要る (-DPARCEL_ENABLE_KS_ARNOLDI=0 で外せば不要. 「ビルドするソルバの取捨」). 入れ方の例を示す. パッケージ名は OS の版や追加のリポジトリ (RHEL 系の CRB など) によって異なりうる. RHEL 系の行は Rocky Linux 9, Ubuntu 系の行は Ubuntu 24.04 で確かめた.

OS など 入れ方の例
RHEL 系 dnf install openblas-devel (CRB を有効にしてから. 「前もって用意するもの」)
Ubuntu 系 apt install libopenblas-dev liblapacke-dev
macOS brew install openblas (「macOS (Homebrew)」)
spack spack install openblas (OpenBLAS は LAPACKE を含む)
富士通の環境 (Odyssey) 入れる必要はない. 実装は富士通 LAPACK (-lfjlapack. 富士通の言語環境に含まれる) を使い, ヘッダは OS の OpenBLAS のlapacke.hを借りる (下を参照)

　入れたヘッダとライブラリの場所は次のように調べる.

find / -name lapacke.h 2>/dev/null               # ヘッダを探す
rpm -ql openblas-devel | grep -E 'lapacke.h|\.so$'   # RHEL 系: パッケージが入れたファイル
dpkg -L liblapacke-dev | grep -E 'lapacke.h|\.so$'   # Ubuntu 系: パッケージが入れたファイル
ldconfig -p | grep -E 'liblapacke|libopenblas'        # Ubuntu 系: OpenBLAS の .so は別のパッケージにあるので, 読める場所から探す
ls $(spack location -i openblas)/include $(spack location -i openblas)/lib   # spack
  • ヘッダが/usr/include/openblas/lapacke.hにあれば-I/usr/include/openblasを付ける. /usr/include/lapacke.hのように標準の場所にあれば-Iは要らない.
  • ライブラリは, OpenBLAS が LAPACKE を含む場合 (spack の OpenBLAS など) は-lopenblasだけでよい. LAPACKE が別のライブラリ (liblapacke.so) の場合は-llapacke -lopenblasのように両方を付ける. 標準の場所に無いライブラリは-L<場所>と-Wl,-rpath,<場所>も付ける.
  • Rocky Linux 9 (RHEL 9 系) では, openblas-develでヘッダは/usr/include/openblas/lapacke.h, OpenBLAS (libopenblas.so) が LAPACKE を含むので, -I/usr/include/openblas -lopenblas (クイックスタートの指定のまま) でよい. lapack-develは要らない (入れると別に/usr/include/lapacke/lapacke.hとliblapacke.soが入る).
  • Ubuntu 24.04 では, libopenblas-devとliblapacke-devでヘッダは/usr/include/lapacke.h (-Iは不要), OpenBLAS は LAPACKE を含まないので-llapacke -lopenblasとする. -lopenblasだけでは, ks_arnoldiを使うプログラムのリンクでLAPACKE_dgeevなどが見つからない (使わないプログラムはリンクできてしまうので気付きにくい).
  • install_stack.shで入れた環境 (setup.shを読んだシェル) では, spack の OpenBLAS (spack location -i openblasのinclude/とlib/) を使う. setup.shは spack の環境のビューのlib/をLD_LIBRARY_PATHに加えるので, OS の LAPACKE とリンクすると, OS の BLAS が spack のlibopenblas.so.0を読み, 実行時にsymbol lookup error: ... undefined symbol: sgemv_thread_nなどで止まる.
  • 富士通の環境 (Odyssey) では, ヘッダに OS の OpenBLAS のlapacke.h (-I/usr/include/openblas) を, 実装に富士通 LAPACK (-lfjlapack) を指定する. 富士通 LAPACK は富士通の言語環境のlib64/にあるので, その場所を-Lと-Wl,-rpathで与える (例: -L$fj_root/lib64 -Wl,-rpath,$fj_root/lib64 -lfjlapack. fj_rootは「Odyssey」の「使用時の設定」で定義する). ビルドの全体はインストールの「推奨オプション」の「Odyssey」にある.
  • Python のパッケージでは, 同じ値をビルドの設定LAPACKE_INCLUDE_DIR (ヘッダのディレクトリ) とLAPACK_LIBS (リンクのフラグ) で与える (「ビルドの設定」).
  • spack のレシピ parcel-sycl を使う場合は, レシピが OpenBLAS の場所を自動で与える.
